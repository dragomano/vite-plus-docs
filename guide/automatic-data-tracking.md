# Автоматическое отслеживание данных {#automatic-data-tracking}

Автоматическое отслеживание данных — это механизм, с помощью которого Vite Task определяет, какие входные данные нужны задаче для кэширования результатов без явной настройки.

Когда вы запускаете задачу с включённым кэшированием, Vite Task отслеживает выполнение задачи и сохраняет информацию о прочитанных и записанных файлах, а также любые метаданные, переданные задачей. При следующем запуске Vite Task использует сохранённый отпечаток, чтобы определить, нужно ли использовать кэш или повторно выполнить задачу.

Используйте эту страницу, если вам нужно понять, почему задача использовала кэш или почему кэш был пропущен, а также если нужно решить, следует ли добавлять настройки `cache.input`, `cache.output`, `cache.env` или `cache.untrackedEnv`.

## Уровни отслеживания {#tracking-tiers}

Автоматическое отслеживание данных имеет два уровня:

| Уровень | Применяется к | Что отслеживается |
| --- | --- | --- |
| Отслеживание файловой системы | Всем задачам с включённым кэшированием | <ul><li>Файлы, прочитанные командой</li><li>Проверки отсутствующих файлов</li><li>Содержимое списков каталогов</li><li>Созданные выходные файлы</li></ul> |
| Кооперативное отслеживание | Инструментам, предоставляющим данные для кэша (`vp build`, `vp test`) | <ul><li>Переменные окружения, переданные инструментом</li><li>Пути, управляемые инструментом, которые не должны считаться входными или выходными данными, например `node_modules/.vite-temp`</li></ul> |

Vite Task начинает с отслеживания файловой системы для любой команды. Инструмент, предоставляющий данные для кэша, может добавить информацию, известную только самому инструменту во время выполнения.

## Отслеживание файловой системы {#file-system-tracking}

Отслеживание файловой системы применяется к каждой задаче с включённым кэшированием. Если вы не указываете [`cache.input`](/config/run#cache-input), Vite Task отслеживает файлы, которые команда читает во время выполнения:

```ts [vite.config.ts]
import { defineConfig } from 'vite-plus';

export default defineConfig({
  run: {
    tasks: {
      build: {
        command: 'tsc',
      },
    },
  },
});
```

Для этой задачи Vite Task сохраняет информацию об исходных файлах, файлах конфигурации, отсутствующих файлах, которые проверяла команда, и каталогах, которые команда просматривала. При последующих запусках задача будет выполняться заново, если один из этих отслеживаемых входных файлов изменится.

Отслеживание файловой системы также учитывает выходные данные. Если вы не указываете [`cache.output`](/config/run#cache-output), Vite Task архивирует файлы, созданные командой после успешного выполнения, и восстанавливает их при попадании в кэш.

### Пересобираемые входные данные {#rebuildable-inputs}

Некоторые инструменты читают файлы, в которые они же и записывают:

- При включённом [`exports`](https://tsdown.dev/options/package-exports) tsdown читает `package.json` и записывает обратно сгенерированное поле `exports`.
- Многие инструменты сборки перечисляют `dist`, чтобы удалить прежнюю сборку перед записью новой.
- Инструменты со своим кэшем читают его и записывают обратно, как это делает `tsc --incremental` с `tsconfig.tsbuildinfo`.

Этот раздел объясняет, как Vite Task работает с файлами и каталогами, которые задача и читает, и записывает.

Vite Task называет такие файлы и каталоги **пересобираемыми**: задача создаёт их сама, поэтому до её запуска они не обязаны существовать. Задача может пересобрать:

- Файлы, которые она записывает, например `dist/index.mjs` или `package.json`, который обновляет tsdown.
- Каталоги, в которых задача записала всё содержимое, например `dist`.

::: warning
Пересобираемые входные данные предполагают, что задача не изменяет свои выходные данные, пока входные остаются прежними.

Например, скрипт, который при каждом запуске дописывает данные в файл, нарушает это предположение, и Vite Task не может это обнаружить. Vite Task кэширует файл в том виде, в каком его оставил скрипт, поэтому следующий запуск попадает в кэш и восстанавливает файл, ничего не дописывая.
:::

После завершения задачи Vite Task снимает отпечаток её входных данных в том виде, в каком их оставила задача. При следующем запуске:

- Пересобираемый входной файл может отсутствовать — например, после свежего клонирования или если вы его удалили. Кэш всё равно срабатывает и восстанавливает его вместе с выходными данными задачи.
- Пересобираемый файл, который существует, должен совпадать с тем, что оставила задача. Если его изменило что-то другое, происходит промах кэша.
- Непересобираемые входные данные, например исходные файлы, по-прежнему проверяются строго. Удаление или правка любого из них приводят к промаху кэша.

#### Пример: задача переписывает исходные файлы {#example-a-task-rewriting-sources}

```ts [vite.config.ts]
tasks: {
  build: {
    // `--exports` заставляет tsdown записывать сгенерированное поле `exports` в package.json.
    command: 'tsdown --exports',
  },
}
```

```
my-lib/
├── src/
│   └── index.ts             # входные данные: tsdown читает файл
└── package.json             # пересобираемый: tsdown читает файл, а затем записывает в него "exports"
```

При следующем запуске Vite Task сравнивает `package.json` с файлом, который записал tsdown, поэтому добавленное tsdown поле `exports` не приводит к промаху кэша:

```bash
$ vp run build               # первый запуск: tsdown добавляет "exports" в package.json
$ vp run build               # попадание в кэш
```

Правка `package.json` вручную по-прежнему приводит к промаху кэша, и это правильно, потому что tsdown должен запуститься заново с вашими изменениями:

```bash
$ vp pm pkg set version=1.1.0
$ vp run build               # промах кэша: 'package.json' изменён
```

#### Пример: задача перечисляет свой выходной каталог для удаления {#example-a-task-listing-its-output-folder-for-deletion}

```ts [vite.config.ts]
tasks: {
  build: {
    // `--clean` удаляет прежнюю сборку в `dist`, прежде чем tsdown запишет новую.
    command: 'tsdown --clean',
  },
}
```

```
my-lib/
├── src/
│   └── index.ts             # входные данные
├── package.json             # входные данные
└── dist/                    # пересобираемый: задача записала всё содержимое
    └── index.mjs            # пересобираемый: задача записывает файл
```

Перечисление `dist` делает его входными данными. Поскольку задача записала всё содержимое `dist`, весь каталог становится пересобираемым:

```bash
$ vp run build               # первый запуск: tsdown записывает dist/
$ rm -rf dist                # как при свежем клонировании
$ vp run build               # попадание в кэш: dist/ восстановлен
```

Вам не нужно указывать `'!dist/**'` в `cache.input`, чтобы исключить `dist` из входных данных задачи, даже хотя задача перечисляет `dist` для удаления прежней сборки, а затем записывает новую.

#### Пример: задача читает и записывает свой собственный кэш {#example-a-task-reading-and-writing-its-own-cache}

```ts [vite.config.ts]
tasks: {
  typecheck: {
    command: 'tsc --incremental --noEmit',
  },
}
```

```
my-app/
├── src/
│   └── main.ts              # входные данные: tsc читает файл
├── tsconfig.json            # входные данные: tsc читает файл
└── tsconfig.tsbuildinfo     # пересобираемый: tsc читает из него свой кэш, а затем записывает его обратно
```

Vite Task сравнивает `tsconfig.tsbuildinfo` с файлом, который записал tsc, поэтому обновления tsc не приводят к промаху кэша. Если файла нет — например, после свежего клонирования, — попадание в кэш восстанавливает его:

```bash
$ vp run typecheck           # первый запуск: tsc записывает tsconfig.tsbuildinfo
$ vp run typecheck           # попадание в кэш
$ rm tsconfig.tsbuildinfo    # как при свежем клонировании
$ vp run typecheck           # попадание в кэш: tsconfig.tsbuildinfo восстановлен
```

#### Не кэшируйте задачи, которые изменяют файлы на месте {#avoid-caching-tasks-that-modify-files-in-place}

Задача, которая переписывает ваши исходные файлы, делает их пересобираемыми. Если кэшированный `vp fmt` переписывает все файлы в `src/utils`, весь каталог становится пересобираемым:

```
src/
└── utils/                   # пересобираемый: vp fmt переписал всё содержимое
    ├── a.ts                 # пересобираемый: vp fmt переписал файл
    └── b.ts                 # пересобираемый: vp fmt переписал файл
```

Тогда удаление `src/utils` — это попадание в кэш, которое записывает каталог обратно.

Отключите автоисправления в кэшируемых задачах линтинга и форматирования:

```ts [vite.config.ts]
tasks: {
  lint: 'vp lint', // вместо `vp lint --fix`
  format: 'vp fmt --check', // вместо `vp fmt`
}
```

### Ограничения {#limitations}

Vite Task не может отслеживать чтение переменных окружения и не всегда может определить, какие из отслеживаемых путей являются стабильными входными данными, сгенерированными выходными файлами или управляемыми инструментом путями кэша, которые не должны становиться входными или выходными данными.

Используйте раздел [Переопределение входных и выходных данных](#override-inputs-and-outputs), если отслеживание файловой системы включает файлы, которые не должны влиять на кэш, не учитывает файлы, которые должны влиять на кэш, или восстанавливает неправильные выходные файлы.

Используйте [`cache.env`](/config/run#cache-env), если команде требуется переменная окружения и её значение должно влиять на кэш, либо [`cache.untrackedEnv`](/config/run#cache-untrackedenv), если значение не должно влиять на кэш.

Эти ограничения не распространяются на `vp build`: Vite автоматически передаёт метаданные [кооперативного отслеживания](#cooperative-tracking), включая `VITE_*`, `NODE_ENV` и управляемые Vite пути кэша, которые не должны становиться входными или выходными данными. Стандартная задача `vp build` не требует ручной настройки `input`, `output` или `env`.

### Переопределение входных и выходных данных {#override-inputs-and-outputs}

[`cache.input`](/config/run#cache-input) определяет, какие изменения приводят к инвалидированию кэша. [`cache.output`](/config/run#cache-output) определяет, какие файлы Vite Task восстанавливает при попадании в кэш.

Обе настройки используют одинаковый синтаксис и могут конфигурироваться независимо друг от друга.

- Не указывайте параметр, чтобы сохранить автоматическое отслеживание.
- Добавьте `{ auto: true }`, чтобы сохранить автоматическое отслеживание и одновременно добавить правила с glob-шаблонами.
- Используйте строковые glob-шаблоны для включения путей.
- Используйте glob-шаблоны с `!` для исключения путей.
- Используйте `[]`, чтобы заменить автоматическое отслеживание пустым списком.

```ts [vite.config.ts]
tasks: {
  build: {
    command: 'node build.mjs',
    cache: {
      // Сохранить автоматическое отслеживание входных данных, но исключить `dist` из входов.
      input: [{ auto: true }, '!dist/**'],

      // Отключить автоматическое отслеживание выходных данных и восстанавливать только `dist/**` при попадании в кэш.
      output: ['dist/**'],
    },
  },
}
```

Используйте явные glob-шаблоны для `input` только в том случае, если вы точно знаете полный набор входных данных команды. Эта задача линтинга переопределяет только входные данные, поэтому отслеживание выходных данных остаётся автоматическим:

```ts [vite.config.ts]
tasks: {
  lint: {
    command: 'vp lint',
    cache: {
      // Отключить автоматическое отслеживание входных данных и учитывать в отпечатке только эти файлы.
      input: ['src/**', 'vite.config.ts'],
    },
  },
}
```

Установите `input: []`, если никакие файлы не должны влиять на отпечаток кэша. Это требуется редко. Например, задача загрузки может использовать кэш, если один и тот же URL всегда возвращает один и тот же файл. Для такой задачи не нужно вычислять отпечаток по входным файлам, но изменение URL всё равно должно инвалидировать кэш:

```ts [vite.config.ts]
tasks: {
  downloadSchema: {
    command: 'curl -O https://example.com/schema.json',
    cache: {
      input: [],
    },
  },
}
```

Установите `output: []`, если никакие файлы не должны восстанавливаться при попадании в кэш.

## Кооперативное отслеживание {#cooperative-tracking}

Отслеживание файловой системы фиксирует обращения к файлам. Оно не может определить, зачем инструмент использовал каждый из путей.

`vp build` знает о сборке Vite больше, чем Vite Task может определить только по обращениям к файлам. Когда `vp build` выполняется с включённым кэшированием, Vite передаёт эти метаданные в Vite Task. Vite Task объединяет этот отчёт с данными отслеживания файловой системы, чтобы создать более точный отпечаток кэша.

Для стандартной сборки Vite вам не нужно добавлять эти записи вручную, поскольку Vite автоматически передаёт их во время выполнения:

- `env: ['VITE_*']` или `env: ['NODE_ENV']`
- исключения входных или выходных данных для временных путей, таких как `node_modules/.vite-temp`

Такие выходные данные сборки, как `dist`, фиксируются автоматическим отслеживанием файловой системы и восстанавливаются при попадании в кэш.

Вам нужно только определить задачу с помощью `vp build`:

```ts [vite.config.ts]
import { defineConfig } from 'vite-plus';

export default defineConfig({
  run: {
    tasks: {
      frontendBuild: 'vp build',
    },
  },
});
```

Запустите эту задачу с помощью `vpr frontendBuild` или `vp run frontendBuild`.

Ручная настройка переопределяет переданные метаданные. Добавляйте `cache.input`, `cache.output`, `cache.env` или `cache.untrackedEnv`, если в вашем проекте есть поведение, которое Vite не может автоматически определить.

Vite+ поддерживает кооперативное отслеживание для `vp build` и `vp test`. Команда `vp test` сообщает о путях кэша Vitest на диске (`node_modules/.vitest-cache` и кэш результатов в каталоге кэша Vite), поэтому они не инвалидируют задачу и не восстанавливаются в неё. В будущем эта поддержка будет расширена на другие официальные инструменты. Сторонние инструменты могут передавать метаданные кэша с помощью [`@voidzero-dev/vite-task-client`](https://npmx.dev/package/@voidzero-dev/vite-task-client).

## Когда добавлять ручную настройку {#when-to-add-manual-config}

Добавляйте настройку, когда в проекте есть поведение, о котором команда или инструмент не могут узнать автоматически. Эти параметры указываются внутри объекта [`cache`](/config/run#cache) задачи.

| Случай                                                                             | Пример                                                                                          |
| ---------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Исключить каталог выходных данных из входных данных                                | `input: [{ auto: true }, '!dist/**']`                                                           |
| Исключить временный сгенерированный файл из отслеживания входных и выходных данных | `input: [{ auto: true }, '!.tmp/config.mjs']`<br>`output: [{ auto: true }, '!.tmp/config.mjs']` |
| Избежать автоматического отслеживания файлов для задачи                            | `input: ['src/**']`<br>`output: ['dist/**']`                                                    |
| Отслеживать и передавать переменную окружения                                      | `env: ['NODE_ENV']`                                                                             |
| Передавать переменную окружения без добавления в отпечаток кэша                    | `untrackedEnv: ['GITHUB_ACTIONS']`                                                              |
