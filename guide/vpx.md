# Запуск бинарных файлов {#running-binaries}

Используйте `vpx`, `vp exec` и `vp dlx` для запуска бинарных файлов пакетов и сценариев без переключения между локальными установками, загруженными пакетами и инструментами, специфичными для проекта.

## Обзор {#overview}

В зависимости от первого аргумента `vpx` делает одно из двух:

- [`vpx <package>`](#running-package-binaries) запускает бинарный файл из локального или удалённого npm-пакета, как `npx`.
- [`vpx <file>`](#running-scripts) запускает файл TypeScript или JavaScript, как `tsx`, а [`vpx --watch <file>`](#watch-mode) запускает его снова, когда изменяется используемый им файл, как `tsx watch`.

Остальные команды дают более строгий контроль над тем, откуда берётся бинарный файл:

- [`vp exec`](#vp-exec) запускает команду из локальных каталогов `node_modules/.bin`, а если она не найдена — из `PATH`.
- [`vp dlx`](#vp-dlx) запускает бинарный файл пакета без добавления его в зависимости.

`vpx -v` или `vpx --version` выводит версию Vite+, как `vp --version`. В сценариях `package.json` `vpx` выводит версию пакета `vite-plus` проекта.

## Запуск бинарных файлов пакетов {#running-package-binaries}

```bash
vpx [options] <pkg[@version]> [args...]
```

`vpx` ищет бинарный файл по порядку в локальных каталогах `node_modules/.bin`, в глобальных пакетах под управлением Vite+ и в системном `PATH`. Если нигде его нет, `vpx` загружает пакет и запускает его через `vp dlx`. При использовании `pkg@version`, `--package/-p` или `--shell-mode` он запускается напрямую через `vp dlx`.

### Параметры {#options}

- `-p, --package <name>` устанавливает один или несколько дополнительных пакетов перед выполнением команды
- `-c, --shell-mode` выполняет команду внутри оболочки
- `-s, --silent` подавляет вывод Vite+ и отображает только вывод выполняемой команды

### Примеры {#examples}

```bash
vpx eslint .
vpx create-vue my-app
vpx oxlint@1.85.0 --version
vpx -p cowsay -c 'echo "hi" | cowsay'
```

Менеджеры пакетов и `vp run` помещают `node_modules/.bin` первыми в `PATH`, поэтому сценарии `package.json` запускают бинарный файл `vpx` из пакета `vite-plus` проекта. Этот бинарный файл не требует глобального CLI и ищет только в локальных каталогах `node_modules/.bin`. Он запускает установленный бинарный файл напрямую, как глобальный `vpx`, а `pkg@version`, `--package/-p` или `--shell-mode` — через `vp dlx`. Отсутствие установленного бинарного файла считается ошибкой, поэтому сценарий никогда случайно не загрузит пакет:

```
error: vpx: 'eslint' is not installed in node_modules
note: Add it to devDependencies, or run `vp dlx eslint` to download and run it.
```

## Запуск сценариев {#running-scripts}

```bash
vpx [--tsconfig <path>] [node options] <file> [args...]
```

`vpx` запускает файлы TypeScript и JavaScript напрямую, без зависимости от `tsx` или `ts-node`. Сценарии выполняются на версии Node.js проекта — той же, которую выбирает [`vp node`](/guide/env), — с загрузчиком [oxc-node](https://github.com/oxc-project/oxc-node), поставляемым вместе с Vite+.

```bash
vpx ./scripts/seed.ts --dry-run
vpx scripts/build.mts
vpx --watch ./server.ts
vpx --env-file=.env ./scripts/migrate.ts
vpx --tsconfig tsconfig.scripts.json ./tools/gen.ts
```

### Файлы и имена пакетов {#files-and-package-names}

`vpx` выполняет свой аргумент как файл, если он:

- путь (начинающийся с `./`, `../` или `/`; в Windows также `.\`, `..\`, диск, например `C:\`, или `\\`), который заканчивается на `.ts`, `.mts`, `.cts`, `.tsx`, `.js`, `.mjs`, `.cjs` или `.jsx`
- имя с одним из этих расширений, существующее в виде файла, например `scripts/seed.ts`
- путь к файлу, в shebang которого запускается `vpx` (см. [Сценарии с shebang](#shebang-scripts))

Отсутствующий путь или отсутствующее имя с расширением TypeScript считается ошибкой: `vpx` никогда не загружает пакет для него. После параметров Node.js, например `vpx --inspect seed.ts`, только об отсутствующем пути сообщает сам `vpx`; об отсутствующем имени сообщает Node.js. Имя с расширением JavaScript, не являющееся файлом, например `highlight.js`, запускает пакет с таким именем.

### Поддерживаемый синтаксис {#supported-syntax}

- синтаксис TypeScript, который удаление типов Node.js не поддерживает: перечисления, пространства имён, свойства параметров и JSX
- декораторы с `"experimentalDecorators": true`, включая `emitDecoratorMetadata`; стандартные декораторы и поля `accessor` пока не поддерживаются
- `paths` из tsconfig для `import`, импорты `.js`, указывающие на файлы `.ts`, и импорты без расширения
- ESM и CommonJS, включая `require()` файлов `.ts`; файл `.cts` всегда является CommonJS, поэтому в нём используются `import x = require('...')` и `export =`, а объявления `import`/`export` завершаются ошибкой с предложением переименовать файл в `.mts`
- TypeScript, опубликованный в `node_modules`
- `jsx`, `jsxImportSource`, `jsxFactory`, `jsxFragmentFactory`, `useDefineForClassFields` и `verbatimModuleSyntax` из tsconfig; значения по умолчанию см. в разделах [JSX](#jsx) и [tsconfig](#tsconfig)

`vpx` не выполняет проверку типов. Для этого используйте [`vp check`](/guide/check).

### Параметры {#options-1}

- `--tsconfig <path>` применяет один tsconfig ко всем файлам (см. [tsconfig](#tsconfig))
- `--watch` запускает файл снова, когда изменяется используемый им файл (см. [Режим наблюдения](#watch-mode))
- параметры Node.js перед файлом, например `--inspect`, `--test`, `--env-file`, `--require` и `--import`, передаются Node.js; предзагружаемые модули `--require` и `--import` тоже могут быть на TypeScript
- всё, что указано после файла, включая `--`, передаётся сценарию

### Сценарии с shebang {#shebang-scripts}

Сценарии могут использовать `vpx` в качестве интерпретатора. Сделайте файл исполняемым и сохраните его расширение:

```ts
#!/usr/bin/env vpx
// scripts/release.ts
```

### В сценариях `package.json` {#in-package-json-scripts}

Бинарный файл `vpx` из пакета `vite-plus` запускает сценарии самостоятельно, поэтому `"seed": "vpx ./scripts/seed.ts"` работает в сценариях `package.json` без глобального CLI. Он запускает их на том Node.js, который его запустил, а внутри `vp run` и сценариев менеджера пакетов это версия проекта.

### Режим наблюдения {#watch-mode}

```bash
vpx --watch [watch options] [node options] <file> [args...]
```

`vpx --watch` запускает файл и запускает его снова, когда изменяется используемый им файл, как `tsx watch`. Это не собственный режим наблюдения Node.js: вместо него `vpx` использует наблюдатель oxc-node (`oxnode watch`), который запускает файл с загрузчиком `vpx`.

```bash
vpx --watch ./src/server.ts --port 3000
vpx --watch --include "./config/*.json" --exclude "src/**/*.test.ts" ./src/server.ts
vpx --watch --inspect --clear-screen=false ./src/index.ts
```

Он наблюдает за всеми файлами, которые сценарий импортирует или требует (в том числе в рабочих потоках — на Node.js 24 и новее), за файлами tsconfig, которые читает `vpx`, и за теми, которые они `extends`, за файлами, которые искал неудачный импорт, поэтому создание такого файла перезапускает сценарий, а также за файлами `--env-file`. Каталог `node_modules` не наблюдается, если только его не укажет `--include`. Нажмите Enter, чтобы перезапустить сценарий сразу. Ctrl+C останавливает сценарий и наблюдатель; повторное нажатие принудительно завершает процесс. `vpx --watch --help` выводит список параметров:

- `--include <glob>` также наблюдает за подходящими файлами, а `--exclude <glob>` никогда их не наблюдает
- `--clear-screen=false` (или `--no-clear-screen`) сохраняет вывод предыдущих запусков; экран очищается только в терминале
- `--kill-signal <signal>` останавливает сценарий перед перезапуском (по умолчанию `SIGTERM`), а `--kill-timeout <ms>` принудительно завершает его по истечении этого времени (по умолчанию 5000)
- `--rerun-on-enter=false` (или `--no-rerun-on-enter`) оставляет stdin сценарию
- `--poll[=<ms>]` опрашивает файлы вместо использования событий файловой системы — для Docker, WSL и сетевых дисков
- `--tsconfig <path>` применяет один tsconfig ко всем файлам, как и для `vpx <file>`

Работают и параметры `--ignore` и `--no-cache` из `tsx watch`, и его переменная `CHOKIDAR_USEPOLLING` (`--no-cache` ничего не делает: у `vpx` нет кэша преобразований), а также параметры режима наблюдения Node.js `--watch-preserve-output` и `--watch-kill-signal`, поэтому сценарии, написанные для `tsx watch` или `node --watch`, переносятся без изменений. `--watch-path`, который запустил бы собственный режим наблюдения Node.js, приводит к ошибке с указанием на `--include`; так же поступают `--test`, `--eval` и другие параметры, не запускающие файл. Остальные параметры Node.js указываются перед файлом.

### tsconfig

`vpx` читает параметры компилятора из tsconfig, но не выполняет по ним проверку типов. Каждый файл использует ближайший расположенный выше `tsconfig.json`, который включает его через `files`, `include`, `exclude` или `references` проекта, как это делает `tsc`, а `extends` раскрывается. Файлы в `node_modules` не используют tsconfig, как и файл, который не включён ни в один tsconfig, поэтому для него применяются значения по умолчанию, приведённые ниже. Такой файл всё равно разрешает алиасы `paths` через ближайший расположенный выше `tsconfig.json`, как это делает tsx: при корневом tsconfig с `include` в виде `["src"]` сценарий в `scripts/` может импортировать те же алиасы, что и `src/`. Поскольку конфигурация зависит от расположения файла, а не от рабочего каталога, `vpx` компилирует файл одинаково независимо от того, откуда он запущен.

`--tsconfig <path>` применяет одну конфигурацию ко всем файлам, включая файлы, которые эта конфигурация не включает. Без `--tsconfig` то же самое делает переменная окружения `OXC_TSCONFIG_PATH` или `TS_NODE_PROJECT`. Если она указывает на несуществующий файл или tsconfig не удаётся разобрать, `vpx` выводит предупреждение и запускается без этой конфигурации.

Файл, к которому не применяется ни один tsconfig, выполняется так, будто его `compilerOptions` пусты:

| Параметр                          | Без tsconfig                                                                                                                                                                                                                                                                                                                                                                |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `module`                          | Формат модуля определяется значением `"type"` в `package.json`: ESM при `"module"`, иначе CommonJS. `.mts` всегда ESM, а `.cts` всегда CommonJS. При значении `module` в tsconfig `node16`, `node18`, `nodenext`, `es2015` или более позднем файлы `.ts` и `.tsx` выполняются как ESM независимо от `"type"`; для значений `node*` `tsc` и tsx, наоборот, следуют `"type"`. |
| `paths`, `baseUrl`                | Отсутствуют. Импорты разрешаются как в Node.js, а также `.js` в `.ts` или `.tsx`, `.mjs` в `.mts`, `.cjs` в `.cts` и импорты без расширения.                                                                                                                                                                                                                                |
| `useDefineForClassFields`         | `true`: поля класса имеют семантику `[[Define]]` и выполняются нативно, как при `target` = `ES2022` или более позднем. Более низкий `target` переключает их на семантику `[[Set]]`, как в `tsc`.                                                                                                                                                                            |
| `experimentalDecorators`          | `false`: декоратор завершается ошибкой с требованием включить этот параметр.                                                                                                                                                                                                                                                                                                |
| `emitDecoratorMetadata`           | `false`.                                                                                                                                                                                                                                                                                                                                                                    |
| `jsx`, `jsxImportSource`          | Автоматическая среда выполнения с импортом `react/jsx-runtime` (см. [JSX](#jsx)).                                                                                                                                                                                                                                                                                           |
| `verbatimModuleSyntax`            | `false`: импорты, привязки которых не используются во время выполнения, удаляются вместе со своими побочными эффектами.                                                                                                                                                                                                                                                     |
| `rewriteRelativeImportExtensions` | `false`. Импорты вида `./file.ts` работают в любом случае.                                                                                                                                                                                                                                                                                                                  |

Типы удаляются, а перечисления, пространства имён и свойства параметров компилируются независимо от того, что указано в tsconfig. `strict`, `lib` и другие параметры проверки типов не влияют на результат, а `target` изменяет только значение по умолчанию для полей класса.

### JSX

Файлы `.jsx` и `.tsx` компилируются в вызовы среды выполнения JSX, по умолчанию React. Установите используемую среду выполнения — `react` или пакет, указанный в `jsxImportSource`; Vite+ не поставляет её. Среду выполнения выбирают параметры tsconfig:

| tsconfig `jsx`                 | Результат                                                                                                                                          |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| не задано или `"react-jsx"`    | Автоматическая среда выполнения: `jsx()` и `jsxs()` из `<jsxImportSource>/jsx-runtime`, при этом `jsxImportSource` по умолчанию равен `react`      |
| `"react-jsxdev"`               | Среда выполнения для разработки: `jsxDEV()` из `<jsxImportSource>/jsx-dev-runtime`, с именем файла, номером строки и столбца каждого элемента      |
| `"react"`                      | Классическая среда выполнения: `React.createElement()` или `jsxFactory`, при этом фрагменты задаются как `React.Fragment` или `jsxFragmentFactory` |
| `"preserve"`, `"react-native"` | Автоматическая среда выполнения, потому что Node.js не может выполнять JSX                                                                         |

Классическая фабрика, которую импортирует файл, например `import { h, Fragment } from 'my-jsx'`, сохраняется, даже если её использует только JSX.

Директивы-комментарии переопределяют tsconfig для этого файла:

```tsx
/** @jsxImportSource my-jsx */
```

```tsx
/** @jsxRuntime classic */
/** @jsx h */
/** @jsxFrag Fragment */
import { h, Fragment } from 'my-jsx';
```

Если в файле есть и `@jsx`, и `@jsxImportSource`, то `@jsxImportSource` выбирает автоматическую среду выполнения, а `@jsx` игнорируется. Директивы считываются из каждого комментария в файле, поэтому даже обычный комментарий вроде `// @jsxImportSource is set above` меняет среду выполнения.

Файл `.jsx` получает параметры JSX из tsconfig только тогда, когда в этом tsconfig установлено `"allowJs": true`, как в `tsc` и tsx. Иначе используются приведённые выше значения по умолчанию.

JSX, зависящий от плагина компилятора, не поддерживается. `vpx` компилирует JSX только в вызовы экспортов `jsx()`, `jsxs()` и `jsxDEV()` среды выполнения либо в классическую фабрику. Конфигурация, полагающаяся на плагин Babel или сборщика для преобразования JSX — обычно с `"jsx": "preserve"`, — завершается ошибкой во время выполнения или теряет то, что добавляет этот плагин.

### Переход с tsx {#coming-from-tsx}

`vp migrate` переписывает команды tsx в сценариях `package.json` на `vpx` и удаляет dev-зависимость `tsx`, когда tsx больше нигде не используется; см. [Переход с tsx на `vpx`](/guide/migrate-rules#tsx-to-vpx). Большинство сценариев, которые работают с tsx, работают с `vpx` без изменений. Следующие различия могут потребовать правок:

- **JSX по умолчанию**: без параметра `jsx` в tsconfig tsx компилирует JSX в `React.createElement()`, для чего `React` должен быть в области видимости, тогда как `vpx` использует автоматическую среду выполнения. Установите `"jsx": "react"`, чтобы сохранить классический результат. Из-за своего значения по умолчанию tsx также игнорирует одиночный комментарий `/** @jsxImportSource … */`, если только в файле нет `/** @jsxRuntime automatic */` или в tsconfig не задан `"jsx": "react-jsx"`; `vpx` применяет такой комментарий самостоятельно.
- **файлы `.cts` с `import` или `export`**: tsx компилирует их в CommonJS, а `vpx` сообщает об ошибке. Переименуйте файл в `.mts` или запишите его с использованием `import x = require()` и `export =`.
- **`import` в пакете CommonJS**: в пакете без `"type": "module"` tsx компилирует файл `.ts` или `.js`, использующий `import`, `export` или `import.meta`, в CommonJS, поэтому `__filename`, `__dirname` и `require` продолжают работать. `vpx` выполняет такой файл как ES-модуль, как это делает Node.js, поэтому они не определены, а импорт по умолчанию из ES-модуля получает экспорт по умолчанию, а не весь модуль. Используйте вместо этого `import.meta.filename`, `import.meta.dirname` и `createRequire(import.meta.url)`.
- **разрешение `require()`**: tsx сопоставляет `require('./a.js')` с `a.ts` и применяет `paths` из tsconfig к `require()`. `vpx` разрешает `require()` так же, как Node.js, поэтому указывайте расширение `.ts` и используйте алиасы `paths` только с `import`.
- **сигналы**: tsx превращает `SIGINT` и `SIGTERM` в коды выхода 130 и 143 и сначала выполняет обработчики `process.on('exit')`. Под `vpx` сигнал завершает сценарий, как и под Node.js, поэтому освобождайте ресурсы в обработчике `process.on('SIGINT')` или `process.on('SIGTERM')`.
- **версия Node.js**: `vpx` требует Node.js `^22.18.0 || ^24.11.0 || >=26.0.0`, тогда как tsx работает и на более старых выпусках.
- **режим наблюдения**: `tsx watch` превращается в `vpx --watch`, который принимает параметры tsx watch (см. [Режим наблюдения](#watch-mode)). Он также перезапускает сценарий при изменении tsconfig и при создании файла, который искал неудачный импорт, — то, чего tsx watch не делает.
- **eval, REPL и `--check`**: `vpx --eval`, REPL и `vpx --check` не преобразуют TypeScript.
- **`node --import tsx`**: у `vpx` нет аналога для инструментов, которые должны самостоятельно запускать `node`.
- **другие загрузчики**: удалите `--import tsx` из `NODE_OPTIONS`. Два загрузчика, зарегистрированные одновременно, конкурируют за одни и те же файлы.

## `vp exec`

Используйте `vp exec`, чтобы запустить инструменты, которые уже установлены в вашем проекте или доступны в вашем окружении.

```bash
vp exec <command> [args...]
```

Примеры:

```bash
vp exec eslint .
vp exec tsc --noEmit
```

## `vp dlx`

Используйте `vp dlx` для разового запуска пакета без добавления его в зависимости проекта.

```bash
vp dlx <package> [args...]
```

Примеры:

```bash
vp dlx create-vite
vp dlx oxlint@1.85.0 --version
```
