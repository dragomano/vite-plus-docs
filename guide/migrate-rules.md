# Правила миграции {#migration-rules}

Этот справочный раздел подробно описывает, что именно делает команда `vp migrate` с проектом: как она обновляет зависимости, переписывает импорты в исходном коде и сценарии пакетов, а также изменяет конфигурацию менеджера пакетов. Общее описание команды и процесса миграции см. в [руководстве по миграции](./migrate.md).

За исключением раздела [Перед миграцией](#before-you-migrate), в котором перечислены действия, выполняемые вручную, всё, что описано ниже, происходит автоматически.

## Перед миграцией {#before-you-migrate}

1. Выполните `vp upgrade`, чтобы глобальная CLI получила последние правила миграции. Устаревшая локальная версия `vite-plus` не является препятствием: если локальная копия проекта старее, миграция будет выполняться глобальной CLI.
2. При необходимости обновите проект до Vite 7+ и Vitest 4+.
3. Выполните `vp migrate` из корня рабочего пространства. В автоматизированных средах используйте флаг `--no-interactive`.
4. Проверьте все изменённые манифесты, конфигурацию менеджера пакетов, изменения исходного кода и сгенерированный lock-файл.
5. Выполните проверку с помощью `vp install`, `vp check`, `vp test` и `vp build`.

Миграция является идемпотентной: повторный запуск после успешной миграции не должен приводить к появлению новых изменений.

## Обновление или полная настройка {#upgrade-vs-full-setup}

Если проект уже использует `vite-plus`, команда `vp migrate` выполняет только обновление: обновляет зависимости и конфигурацию менеджера пакетов, а также завершает обновление импортов. При этом первоначальная настройка проекта не затрагивается.

- Флаг `--full` дополнительно выполняет действия по настройке: устанавливает git-хуки, настраивает редактор, создаёт файлы для ИИ-агентов, переносит конфигурации ESLint, Prettier, tsup и tsx, добавляет совместимость с фреймворками, исправляет параметр `baseUrl` в `tsconfig` и преобразует Volta в `.node-version`.
- Флаги `--hooks`, `--agent` и `--editor` позволяют выполнить только одно из этих действий без использования `--full`.

Если при обычном обновлении пропускаются действия по настройке, которые можно было бы применить, команда выведет подсказку выполнить `vp migrate --full`. Для новых проектов (не использующих Vite+) всегда выполняется полная миграция.

## Наследование JSON в Oxlint {#oxlint-json-inheritance}

Если `.oxlintrc.json` или `.oxlintrc.jsonc` использует `extends`, `vp migrate` разрешает каждый путь к файлу относительно конфигурации, в которой он объявлен. Команда создаёт общие конфигурации TypeScript и импортирует их через `lint.extends`, включая вложенное наследование. Oxlint применяет существующий порядок слияния, строгости правил и overrides. Обычный `vp lint` использует перенесённые правила без флага `-c`.

Миграция предполагает, что проекты используют ESM. Общие конфигурации превращаются в соседние файлы `.ts`. Импорты из конфигураций JavaScript и TypeScript используют спецификаторы `.js`, которые Vite и TypeScript разрешают в сгенерированные исходные файлы без изменения настроек компилятора. Директивы TypeScript уровня файла остаются перед сгенерированными импортами. Потребители в рабочем пространстве переиспользуют одни и те же сгенерированные модули, включая рабочее пространство, владеющее общей конфигурацией. Значения по умолчанию миграции остаются в локальном блоке `lint` каждого рабочего пространства. Изменяйте эти файлы TypeScript, чтобы обновлять общие настройки. Исходные общие файлы JSON и JSONC остаются доступными другим потребителям; изменения в этих исходных файлах не обновляют перенесённые конфигурации.

Объявления JS-плагинов остаются в исходной конфигурации или override. Относительные пути к плагинам во время выполнения становятся абсолютными через `fileURLToPath(new URL(..., import.meta.url))`. Явно унаследованные настройки `typeAware` и `typeCheck` имеют приоритет над значениями по умолчанию миграции.

Очистка удаляет каждую завершённую символическую ссылку рабочего пространства независимо. Общие алиасы, оставшиеся на диске, сохраняют доступность своих целей и зависимостей.

Владелец общей конфигурации сохраняет `env`, `globals`, `settings` и `ignorePatterns` на верхнем уровне своего блока `lint` через ссылки на общий модуль. Изменения этих полей применяются к владельцу. Другие потребители их не наследуют.

Сгенерированные модули содержат маркер источника. Последующая попытка миграции переиспользует эти модули, не заменяя правки пользователя, поэтому сохранённый потребитель может мигрировать после устранения конфликта. Существующие модули без подходящего маркера по-прежнему считаются конфликтом.

Неудачные слияния и существующие блоки `lint` записывают в конфигурацию Vite отложенный маркер, поэтому отдельный сбой можно повторить после устранения конфликта. Успешное слияние удаляет этот маркер. Завершённые слияния рабочего пространства записывают маркер завершения, включая конфигурации, слитые встроенным образом. После исправления нечитаемой конфигурации снова выполните `vp migrate`, чтобы перенести остальных потребителей и удалить ставшие ненужными файлы JSON.

Импорты общих конфигураций используют литеральные пути, чтобы Vite и TypeScript могли разрешать имена файлов, содержащие `#` или `%`. Относительный путь импорта, содержащий `?` или буквальную обратную косую черту, требует ручной миграции: Vite воспринимает `?` как разделитель запроса, а TypeScript — обратную косую черту как разделитель пути. В этих случаях миграция сохраняет JSON-конфигурацию и выводит предупреждение.

Отсутствующие файлы, некорректный JSON, циклы наследования, конфликтующие выходные файлы и локальные плагины пакета, которые разрешаются иначе, чем относительно каталога конфигурации Vite, приводят к предупреждению, а исходная конфигурация остаётся на месте. Конфигурации за пределами проекта или рабочего пространства, конфигурации внутри `node_modules`, конфигурации Vite в CommonJS и существующий блок `lint` требуют ручного слияния. Удаление JSON-файлов рабочего пространства выполняется только после того, как известны все результаты миграции. Сохранённые потребители JSON сохраняют свои транзитивные зависимости, включая конфигурации, владельцы которых успешно перенесены. Если граф наследования прочитать не удаётся, JSON-файлы рабочего пространства сохраняются, а их владельцы используют общие модули, поскольку недоступный для чтения потребитель может ссылаться на них. `vp lint` по-прежнему отклоняет строковые пути в `lint.extends`; разрешение путей выполняется только во время миграции.

## Конфигурация Pack {#pack-configuration}

`vp migrate` обновляет статические объекты `pack` в `vite.config.*` и экспортируемые объекты в `tsdown.config.*` для [tsdown 0.23](https://github.com/rolldown/tsdown/releases/tag/v0.23.0).

Это также выполняется в существующих проектах Vite+ без `--full`, включая пакеты workspace. Поддерживаются массивы и объекты, напрямую возвращаемые колбэками `defineConfig`. Конфигурации tsdown в формате JSON получают те же обновления после их объединения с `vite.config.ts`.

| Предыдущая опция                                                     | Обновлённая опция                                                                      |
| -------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `bundle: false`                                                      | `unbundle: true`                                                                       |
| `bundle: true`                                                       | Удалена; сборка по-прежнему выполняется по умолчанию                                   |
| `outExtension`                                                       | `outExtensions`                                                                        |
| `publicDir`                                                          | `copy`                                                                                 |
| `removeNodeProtocol: true`                                           | `nodeProtocol: 'strip'`                                                                |
| `injectStyle`                                                        | `css.inject`                                                                           |
| `inlineOnly` / `deps.onlyAllowBundle`                                | `deps.onlyBundle`                                                                      |
| `noExternal`                                                         | `deps.alwaysBundle`                                                                    |
| `skipNodeModulesBundle: true` / `deps.skipNodeModulesBundle: true`   | `deps.neverBundle: true`                                                               |
| `dts.tsgo` / `dts.oxc`                                               | Выбор выполняется через `dts.generator`; объекты параметров генератора сохраняются, а логические флаги удаляются |
| `dts.cjsReexport`                                                    | Удалена; tsdown генерирует объявления CJS отдельно                                     |
| `--public-dir` в скриптах `tsdown` или `vp pack`                     | `--copy`                                                                               |

Миграция проверяет установленную в проекте версию tsdown перед финальной установкой зависимостей. Для конфигураций Pack в Vite+ она читает установленный `vite-plus/dist/toolchain.json`. Это включает файлы `tsdown.config.*`, которые уже импортируют `vite-plus/pack` до того, как миграция перепишет импорты. Автономные конфигурации tsdown используют установленную версию tsdown. Более старые установки Vite+ без этого манифеста сохраняют прежние значения по умолчанию. Для tsdown 0.23 и новее совместимые значения по умолчанию не добавляются. Для более старых или неизвестных версий прежние значения по умолчанию сохраняются: при отсутствии `deps.resolveDepSubpath` ему присваивается значение `true`. Для включённых проверок ATTW, если профиль не задан, устанавливается `profile: 'strict'`. Явные значения, включая `false`, остаются без изменений.

Добавленные настройки содержат комментарии со ссылками на документацию и инструкциями по переходу на новые значения по умолчанию. Удалите `deps.resolveDepSubpath: true`, чтобы [сохранить внешние импорты подмодулей в исходном виде](https://tsdown.ru/options/dependencies#deps-resolvedepsubpath). Удалите добавленный `attw.profile: 'strict'`, чтобы использовать новый профиль разрешения `esm-only` [профили разрешения](https://tsdown.ru/options/lint#profiles). Это отключает проверки разрешения `node10` и CommonJS. Сохраняйте любую из этих настроек, если вашему пакету требуется прежнее поведение. Миграция не добавляет эти комментарии к явно заданным настройкам.

`noExternal` переносится в `deps.alwaysBundle` с сохранением выражений сопоставления, ссылок и методов колбэков. Существующие значения `deps.alwaysBundle` остаются без изменений.

Если `external` используется вместе с любой из форм `skipNodeModulesBundle`, статические сопоставители и ссылки на локальные константы переносятся в `inputOptions.external` перед установкой `deps.neverBundle`. Объявления констант и ссылки на них остаются без изменений.

Это сохраняет исходные правила сопоставления, включая пути к внешним файлам. Неподдерживаемые сопоставители, конфликтующие `inputOptions` и правила зависимостей, специфичные для объявлений, оставляют объект `pack` без изменений и приводят к предупреждению о необходимости ручной миграции.

Преобразование не выполняет код конфигурации. Объекты с spread-операторами, вычисляемыми ключами или дублирующимися ключами, а также конфликтующие старые и новые опции требуют ручной проверки. Динамические селекторы логических значений остаются без изменений. Не связанные с этим опции Vite и плагинов также остаются без изменений. После миграции выполните `vp pack`, чтобы проверить результат. Требования к Node.js, разрешение модулей TypeScript и возвращаемые значения программного `build()` требуют отдельной проверки.

## Конфигурация кэша задач {#task-cache-configuration}

`vp migrate` переносит `env`, `untrackedEnv`, `input` и `output` с верхнего уровня каждой задачи в объект [`cache`](/config/run#cache) этой задачи. Она обновляет статические объекты `run.tasks` в `vite.config.*`. Это также выполняется в существующих проектах Vite+ без `--full`, включая пакеты workspace.

| Предыдущая конфигурация задачи | Обновлённая конфигурация задачи                        |
| ------------------------------ | ------------------------------------------------------ |
| Без `cache`                    | Добавляет `cache` с перенесёнными настройками          |
| `cache: true`                  | Заменяет `true` перенесёнными настройками              |
| `cache: { ... }`               | Добавляет перенесённые настройки в существующий объект |

```ts
// До
build: {
  command: 'vp build',
  env: ['NODE_ENV'],
  input: [{ auto: true }, '!dist/**'],
},

// После
build: {
  command: 'vp build',
  cache: {
    env: ['NODE_ENV'],
    input: [{ auto: true }, '!dist/**'],
  },
},
```

Перенесённые настройки сохраняют свой текст и отступы, а шаг форматирования, описанный в разделе [После миграции](#after-the-migration), добавляет им отступ внутри `cache`. Комментарии на отдельных строках перед перенесённой настройкой, а также комментарии `//` на той же строке после неё переносятся вместе с ней.

Преобразование не выполняет код конфигурации. Задача остаётся без изменений, а команда выводит предупреждение о необходимости ручной миграции, если задача содержит:

- spread-операторы, вычисляемые, экранированные или дублирующиеся ключи;
- переносимую настройку, записанную как метод, например `input() { ... }`;
- комментарий между переносимой настройкой и её запятой или после последней настройки в `cache`;
- переносимую настройку, которая уже существует в `cache`;
- значение `cache`, отличное от `true` или объектного литерала.

Миграция также предупреждает о задачах в объекте `vite.config.*`, который сам не является экспортируемой конфигурацией, — например, в переменной, на которую ссылается конфигурация, или в объекте, переданном в `mergeConfig`. Задачи, создаваемые в других модулях, например с помощью общей вспомогательной функции, не обнаруживаются. Перенесите их настройки вручную; `vp run` выводит список всех задач, для которых перенос ещё требуется.

При значении `cache: false` перенесённые настройки не окажут никакого эффекта, поэтому решите, удалить их или включить кэширование. В проекте, который в остальном уже мигрирован, `vp migrate` выводит эти предупреждения, не выполняя остальную часть миграции.

## Правила обработки зависимостей {#dependency-rules}

Миграция сохраняет политику объявления менеджера пакетов в проекте. Существующее поле `packageManager` или `devEngines.packageManager` остаётся источником истины, а проект, который опирается только на lock-файл, остаётся без закрепления. В частности, миграция не превращает версию менеджера пакетов, использованную для собственной установки, в новое точное требование для участников проекта или CI. Когда миграция определяет необъявленный менеджер пакетов, она выводит предупреждение и ссылается на `vp env pin` для проектов, которые хотят перейти на явное закрепление.

Что происходит с каждой зависимостью из набора инструментов:

| Зависимость                   | Что происходит                                                                                                                                                              |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `vite-plus`                   | Добавляется в пакет, для которого выполняется миграция; обычные диапазоны версий заменяются на конкретную целевую версию — напрямую или через каталог.                     |
| `vite`                        | Существующие объявления сохраняются и указывают на основной алиас. Пакетам pnpm, которые используют только `vite-plus`, не требуется новая запись `vite` (см. [Vite и overrides](#vite-and-overrides)). |
| `vitest`                      | В типичном случае для Node.js удаляется, поскольку `vite-plus` предоставляет его как транзитивную зависимость. Сохраняется или добавляется только в случаях, когда [требуется прямая зависимость](#when-vitest-is-directly-required). |
| `@vitest/*`                   | Напрямую устанавливаемые пакеты экосистемы синхронизируются с версией Vitest, поставляемой вместе с Vite+ (см. [Пакеты экосистемы Vitest](#vitest-ecosystem-packages)). |
| `@voidzero-dev/vite-plus-test` | Полностью удаляется: из зависимостей, overrides, resolutions и алиасов каталогов. Импорты переписываются на актуальный API `vite-plus/test*`. |

### Выбор версии {#version-selection}

- `vite-plus` закрепляется за конкретной версией CLI, выполняющей миграцию, а не за dist-tag `latest`.
- Алиас `vite` указывает на `@voidzero-dev/vite-plus-core` из того же релиза Vite+.
- Если в манифесте используются каталоги (`catalog:` или именованные ссылки на каталог), миграция сохраняет ссылку и обновляет значение соответствующей записи каталога до конкретной целевой версии набора инструментов.
- Намеренно закреплённые протоколы сохраняются: `workspace:`, `file:`, `link:`, `npm:`, `github:`, Git URL и HTTP URL.
- Миграция синхронизирует все пакеты рабочего пространства, а не только корневой манифест. Общие `overrides` и каталоги остаются в корне рабочего пространства, а зависимости, предоставляющие peer-зависимости, размещаются в каждом пакете, которому они необходимы.

### Vite и overrides {#vite-and-overrides}

Вы можете использовать `vite-plus` в пакете pnpm, не объявляя `vite`. Пакет `vite-plus` включает зависимость `vite`, связанную через алиас с его ядром, которое предоставляет peer-зависимость, необходимую Vitest. При миграции переопределение workspace для других потребителей Vite сохраняется, но `vite` не добавляется в пакет только потому, что он использует `vite-plus`.

Связанные правила:

- Прямое объявление `vite` никогда не удаляется только потому, что в корне рабочего пространства существует `override`.
- Обычные или устаревшие алиасы нормализуются; именованные ссылки на каталог сохраняются.
- В pnpm управляемые ключи `override` используют явный диапазон `@*` (`vite@*`, `vitest@*`). pnpm применяет `override`, заменяя указанную спецификацию во всех манифестах, включая манифесты импортёров. Ключ без диапазона соответствует любой спецификации, включая `catalog:`, после чего `vp up` переписывает эту ссылку на конкретную версию. Диапазон `@*` ограничивает действие `override` семантическими диапазонами версий, которые используются в транзитивных зависимостях и peer-зависимостях. Ссылки `catalog:` при этом остаются ссылками на каталог, который и так разрешает их в ядро Vite+. При миграции проект, в котором всё ещё используется ключ без диапазона, получает новый ключ, при этом выбранный именованный каталог сохраняется.
- Bun дублирует свой основной алиас в качестве прямой зависимости для своего механизма разрешения peer-зависимостей, а структура пакетов npm с browser-провайдерами может потребовать верхнеуровневую зависимость `vite`, чтобы вложенные пакеты Vitest могли разрешить `vite`.

### Когда требуется прямая зависимость от Vitest {#when-vitest-is-directly-required}

Во время миграции локальная зависимость `vitest` сохраняется или добавляется с точной версией, поставляемой вместе с Vite+, если выполняется хотя бы одно из следующих условий:

- установленная зависимость имеет обязательную peer-зависимость от `vitest` (как с точной версией, так и с диапазоном версий);
- пакет использует браузерный режим Vitest или один из дополнительных браузерных провайдеров;
- исходный код или конфигурация TypeScript сохраняют ссылки на исходный `vitest`;
- пакет объявляет зависимость `@nuxt/test-utils`; или
- метаданные зависимостей недоступны, и существующая прямая зависимость `vitest` может удовлетворять неизвестную обязательную peer-зависимость.

Для определения используется информация о peer-зависимостях установленных пакетов, поэтому интеграции вроде `vite-plugin-gherkin` также обрабатываются корректно, даже если их имя не содержит `vitest`.

Если пакет подпадает под эти условия, миграция:

- добавляет `vitest` только в этот пакет, а не во все пакеты рабочего пространства;
- использует существующую ссылку на каталог, если она поддерживается, либо точную поставляемую версию в противном случае;
- сохраняет соответствующее правило `override` или `resolution` на уровне рабочего пространства, чтобы всё дерево зависимостей использовало единственную версию Vitest.

Само по себе объявление peer-зависимости не устанавливает Vitest. Если сохранившаяся запись `peerDependencies.vitest` использует запись каталога, которая будет удалена в ходе миграции, она сначала преобразуется в публичный диапазон версий.

### Пакеты экосистемы Vitest {#vitest-ecosystem-packages}

Официальные пакеты `@vitest/*` обычно выпускаются синхронно с Vitest. Миграция синхронизирует версии тех из них, которые проект устанавливает напрямую, включая `@vitest/coverage-v8`, `@vitest/coverage-istanbul`, `@vitest/ui` и `@vitest/web-worker`:

- если менеджер пакетов поддерживает каталоги, зависимости будут ссылаться на каталог набора инструментов: существующие ссылки `catalog:` или `catalog:<имя>` сохраняются, для пакетов без такой ссылки создаётся запись каталога, а каждая запись обновляется до версии Vitest, поставляемой вместе с Vite+;
- если каталоги не поддерживаются (npm, отдельный проект Bun или версии pnpm/Yarn без поддержки каталогов), записывается конкретная поставляемая версия.

Пакеты, которые **не** синхронизируются:

- `@vitest/eslint-plugin` использует собственную схему версионирования;
- `@vitest/coverage-c8` остановился на более раннем релизе и не имеет версии для Vitest 4;
- сторонние интеграции `vitest-*` сохраняют собственные совместимые версии, хотя их обязательная peer-зависимость от Vitest всё равно может привести к [добавлению прямой зависимости](#when-vitest-is-directly-required).

Для режима браузера Vite+ включает базовую среду выполнения `@vitest/browser` и `@vitest/browser-preview`; при миграции их прямые зависимости удаляются. Провайдер Playwright остаётся опциональным. При миграции используется версия Vitest, входящая в комплект, для `@vitest/browser-playwright` — через предпочтительный каталог инструментов или запись зависимости — и одновременно устанавливается его peer-зависимость `playwright`.

Перед изменением импортов `Migration` определяет использование Playwright, включая устаревшие алиасы `vitest/browser-playwright`, `vitest/browser/providers/playwright` и `vitest/plugins/browser-playwright`.

`vp migrate` восстанавливает удалённые Vite+ алиасы WebDriverIO в `@vitest/browser-webdriverio` и добавляет `^5.0.0`, если провайдер отсутствует. Она обновляет более старые версии, сужает диапазоны, допускающие версии ниже `5.0.0`, обновляет соответствующие записи каталогов и удаляет переопределения, принудительно задающие более старую версию провайдера. Версии и диапазоны, соответствующие минимальным требованиям, остаются без изменений. Миграция обеспечивает наличие требуемой peer-зависимости `webdriverio` и добавляет переопределение `@vitest/browser`, соответствующее входящей в комплект версии Vitest (`resolutions` для Yarn). Последующие обновления провайдера сообщества вы выполняете самостоятельно. См. [Провайдер WebDriverIO от сообщества](./vitest-v5.md#community-webdriverio-provider).

Вложенные правила `overrides` npm и Bun, заданные в виде объектов, сохраняются, поскольку они представляют собой пользовательские области действия, а не обычные закрепления версий.

## Правила переписывания исходного кода {#source-rewrite-rules}

### Импорты `vite` {#vite-imports}

Импорты `vite` и `vite/*` переписываются на `vite-plus` **только в файлах конфигурации**: `vite.config.*`, `vitest.config.*` и любых других конфигурационных файлах, обнаруженных в процессе миграции. Во всех остальных файлах импорты `vite` остаются без изменений по двум причинам:

- `vite-plus` не является гарантированным надмножеством публичного API Vite. Он предоставляет только `defineConfig`, `defineProject`, `lazyPlugins` и `resolveConfigFromFile`, поэтому переписывание таких символов, как `createBuilder` или `loadConfigFromFile` (в том числе в типах вида `typeof import('vite')`), может нарушить работу кода.
- Импорт `vite`, оставленный без изменений, в проекте Vite+ всё равно будет разрешён через алиас `@voidzero-dev/vite-plus-core`.

Для пакетов плагинов (непространственные имена, начинающиеся с `vite-plugin-` или `unplugin-`, а также пакеты, содержащие `vite` в `peerDependencies` или `dependencies`) переписывание не выполняется даже в конфигурационных файлах. Это правило распространяется только на спецификатор `vite`.

`vite/rolldown` и `vite/rolldown/*` никогда не переписываются, потому что `vite-plus` не экспортирует эти подпути; они продолжают разрешаться через алиас ядра.

Дополнения модулей через `declare module 'vite'` подчиняются тем же правилам и сохраняются за пределами файлов конфигурации. Благодаря алиасу ядра они продолжают расширять тот же модуль `@voidzero-dev/vite-plus-core`, тип `UserConfig` которого используется функцией `defineConfig` из `vite-plus`, поэтому после миграции всё продолжает работать. Сам `vite-plus` не экспортирует символ `UserConfig`, поэтому переписанное дополнение `declare module 'vite-plus'` не с чем было бы объединять. Расширения, предназначенные для собственного API `vite-plus`, необходимо писать вручную для `vite-plus`.

### Импорты `vitest` и браузерных модулей {#vitest-and-browser-imports}

- Обычные импорты `vitest` и `vitest/*` переписываются на `vite-plus/test*`.
- Импорты устаревших провайдеров Playwright и WebdriverIO обнаруживаются до переписывания, чтобы не потерять соответствующие необязательные зависимости.
- Пространственные импорты `@vitest/browser*` переписываются на соответствующие экспорты `vite-plus/test/browser*`, при необходимости автоматически добавляя дополнительные провайдеры.
- Уже существующие импорты `vite-plus/test*` остаются без изменений.

### Импорты JS-плагинов Oxlint {#oxlint-js-plugin-imports}

Vite+ включает Oxlint в свой состав, поэтому при миграции отдельная зависимость `oxlint` удаляется. Собственные JS-плагины Oxlint импортируют API для создания плагинов по имени. После удаления зависимости такой импорт перестаёт разрешаться. В результате `vp lint` не может загрузить плагин.

При миграции такие импорты перенаправляются на Vite+:

- `@oxlint/plugins` заменяется на `vite-plus/lint/plugins`.
- `oxlint/plugins-dev` заменяется на `vite-plus/lint/plugins-dev`.
- `oxlint` заменяется на `vite-plus/lint/plugins`, если импорт использует привязку из API для создания плагинов, например `defineRule`, `definePlugin` или `Context`. В старых версиях Oxlint этот API предоставлялся из основной точки входа. Теперь он находится в `@oxlint/plugins`.

Импорт через Vite+ всегда соответствует версии Oxlint, которую включает Vite+. Второй пакет закреплять не требуется. Такой импорт также разрешается из любого пакета, который уже зависит от `vite-plus`.

Миграция оставляет без изменений три формы:

- Импорты `oxlint`, использующие только поверхность конфигурации, например `defineConfig`, `OxlintConfig` или `OxlintOverride`. Они по-прежнему разрешаются через отдельный пакет.
- Импорты `oxlint` по умолчанию и импорты пространства имён. Они не указывают конкретную привязку, поэтому миграция не может определить, какую из двух поверхностей следует использовать.
- Импорты `oxlint` без привязок, предназначенные только для побочных эффектов, по той же причине.

Миграция также пропускает пакет, который объявляет `oxlint` или `@oxlint/plugins` в `dependencies` или `peerDependencies`, либо `@oxlint/plugins` в `optionalDependencies`. Эти зависимости могут предоставлять опубликованный плагин Oxlint. Его потребители могут не использовать Vite+.

При очистке сохраняется зависимость `@oxlint/plugins` для разработки, если исходный код, псевдонимы импортов пакета или собранные плагины по-прежнему ссылаются на неё. Это включает игнорируемые выходные файлы в таких каталогах, как `dist`, `build` и `out`.

### Что никогда не переписывается {#what-is-never-rewritten}

- `declare module 'vitest'` и `declare module '@vitest/browser*'`: дополнения модулей должны сохранять идентичность исходного модуля.
- Ссылки, которые остаются в проекте, такие как `compilerOptions.types`, `require.resolve`, `import.meta.resolve` и `vitest/package.json`, требуют наличия локальной зависимости `vitest` (см. раздел [Когда требуется прямая зависимость от Vitest](#when-vitest-is-directly-required)).
- Если пакет объявляет зависимость `@nuxt/test-utils`, все спецификаторы модулей `vitest` и `vitest/*` сохраняются без изменений во всём пакете: преобразование Nuxt требует использования исходного имени модуля, иначе может быть добавлен дублирующий импорт `vi`. Это исключение не распространяется на соседние пакеты и не касается пространственных импортов `@vitest/browser*`.

Правило линтера `prefer-vite-plus-imports` использует то же исключение для Nuxt, поэтому автоматическое исправление также сохраняет эти импорты.

## Правила переписывания сценариев пакетов {#package-script-rewrite-rules}

Во время миграции команды набора инструментов Vite+ в сценариях `package.json` переписываются с сохранением всех их аргументов:

| До            | После                                                    |
| ------------- | -------------------------------------------------------- |
| `vite`        | `vp dev` или соответствующая подкоманда `vp`             |
| `vitest`      | `vp test`                                                |
| `oxlint`      | `vp lint`                                                |
| `oxfmt`       | `vp fmt`                                                 |
| `tsdown`      | `vp pack`                                                |
| `lint-staged` | `vp staged`                                              |
| `eslint`      | `vp lint`, если выполняется его необязательная миграция  |
| `prettier`    | `vp fmt`, если выполняется его необязательная миграция   |
| `tsup`        | `vp pack`, когда выполняется его необязательная миграция |
| `tsx`         | `vpx`, когда выполняется его необязательная миграция     |
| `oxnode`      | `vpx`, когда выполняется его необязательная миграция     |
| `ts-node`     | `vpx`, для поддерживаемых команд в режиме transpile-only |

Для команд, запускаемых через `bunx`, миграция сохраняет сам `bunx` и его флаг `--bun` (оставляя выбранную пользователем среду выполнения), переписывая только управляемую команду. Исключение — tsx: `bunx tsx` превращается в `vpx`, а `bunx --bun tsx` сохраняет tsx (см. [Переход с tsx на `vpx`](#tsx-to-vpx)). Это также работает, если `bunx` находится после разделителя запуска команд, например `run` или `--`:

| До                                                      | После                                                   |
| ------------------------------------------------------- | ------------------------------------------------------- |
| `bunx --bun vite build`                                 | `bunx --bun vp build`                                   |
| `bunx --bun vitest run`                                 | `bunx --bun vp test run`                                |
| `portless --tailscale run bunx --bun vite`              | `portless --tailscale run bunx --bun vp dev`            |
| `dotenv -e .env.test -- bunx --bun oxlint --type-aware` | `dotenv -e .env.test -- bunx --bun vp lint --type-aware` |

Другие команды, запускаемые через `bunx`, а также иные способы запуска пакетов остаются без изменений.

### Переход с tsx на `vpx` {#tsx-to-vpx}

Когда сценарий `package.json`, задача lint-staged или shebang `#!/usr/bin/env tsx` запускает [tsx](https://tsx.is), миграция предлагает перенести запуск на [`vpx`](/guide/vpx) — раннер сценариев TypeScript от Vite+. Она переписывает сценарии и задачи lint-staged в `package.json` и JSON-файлах lint-staged, а также shebang `#!/usr/bin/env tsx` в файлах сценариев:

| До                                                                         | После                                              |
| -------------------------------------------------------------------------- | -------------------------------------------------- |
| `tsx src/seed.ts --rows 10`                                                | `vpx src/seed.ts --rows 10`                        |
| `tsx watch --include "*.json" src/a.ts`                                    | `vpx --watch --include "*.json" src/a.ts`          |
| `npx tsx a.ts`, `pnpm exec tsx a.ts`, `pnpm dlx tsx a.ts`, `bunx tsx a.ts` | `vpx a.ts`                                         |
| `node --import tsx ./a.ts`                                                 | `node --import vite-plus/register ./a.ts`          |
| `node --import=tsx --test`                                                 | `node --import=vite-plus/register --test`          |
| `NODE_OPTIONS='--import tsx' mocha`                                        | `NODE_OPTIONS='--import vite-plus/register' mocha` |
| `cross-env NODE_ENV=dev tsx a.ts`                                          | `cross-env NODE_ENV=dev vpx a.ts`                  |
| `concurrently "tsx watch a.ts" "vp dev"`                                   | `concurrently "vpx --watch a.ts" "vp dev"`         |

`tsx watch` превращается в `vpx --watch`, но никогда — в `vpx watch`, который запускает npm-пакет `watch`. Параметры Node.js и параметры tsx watch сохраняют свой порядок, а `--no-cache` отбрасывается. Команда в кавычках переписывается только для программ, которые её выполняют, например `concurrently`, `nodemon --exec`, `sh -c` и `cross-env-shell`; кавычечный аргумент других программ, как в `echo "tsx a.ts"`, является данными. `vpx` требует тех же версий Node.js, что и сам Vite+, а миграция уже обновляет несовместимые закрепления среды выполнения до них (см. [Vitest 5](/guide/vitest-v5)).

Обычные формы `node --import tsx` и `node --import=tsx` сохраняют Node.js, его параметры, обёртки и аргументы. Они используют [`vite-plus/register`](/guide/vpx#using-nodejs-directly), поэтому Node.js сохраняет своё поведение при eval, обнаружении тестов и во встроенном режиме наблюдения. Мигрируют и буквальные присваивания `NODE_OPTIONS`, в том числе присваивания через `cross-env` и через известные запускающие программы. `vite-plus/register` принимает `TSX_TSCONFIG_PATH` как запасной вариант. Присваивания, которые также загружают устаревший хук tsx или приводят к команде, по-прежнему нуждающейся в tsx, остаются без изменений.

Для исполняемого файла tsx и устаревших форм загрузчика, таких как `--loader tsx/esm` и `-r tsx/cjs`, миграция сохраняет действующие правила `vpx`. Она сохраняет tsx с предупреждением для `--eval`, `--print` или `--check`, REPL, `--test` без файлов или в режиме наблюдения, записи без расширения файла, а также для команд, которые загружают tsx через `NODE_OPTIONS`. Команды с каналами, переменными или подоболочками тоже остаются без изменений. `vpx` тоже принимает `TSX_TSCONFIG_PATH` как запасной вариант; явный `--tsconfig` имеет приоритет.

Оба пути миграции читают сценарии, которые называет команда, включая локальные модули `--require` и `--import`. Они сохраняют tsx, когда сценарий ещё не существует, например когда его создаёт предыдущая команда, или когда загрузчик Vite+ завершился бы на нём с ошибкой: `require()` файла `./a.js`, который только tsx сопоставляет с `a.ts`, файл `.cts` с `import` или `export`, а также файл, смешивающий `import` с `__dirname`, `__filename`, `require()` или `module.exports` в пакете без `"type": "module"`. Эта проверка пропускает glob-шаблоны и сценарии после `cd` или другого изменения состояния оболочки и читает только файлы, названные командой, а не импортируемые ими модули. Она не ищет другие различия в поведении компилятора, например стандартные декораторы, `paths` из tsconfig в `require()` или значение `module` в tsconfig `node16` или `nodenext`; загрузчик сообщает о них при запуске сценария. Пакет, в котором tsx указан в `dependencies`, `optionalDependencies` или `peerDependencies`, тоже сохраняет его, поскольку замена приходит из dev-зависимости `vite-plus`.

Миграция удаляет dev-зависимость `tsx` только тогда, когда tsx больше нигде не используется: нет сохранённого сценария, нет импорта `tsx` или его подпутей, таких как `tsx/esm/api` (в исходном коде, в выходных файлах сборки или в алиасе поля `imports` файла `package.json`), нет shebang, нет настройки инструмента, такой как `--import=tsx`, в `package.json` или в конфигурации JSON или JavaScript, и нет команды tsx в рабочих процессах CI, в git-хуках или в shell-скриптах. Зависимость корня сохраняется, пока tsx использует любой пакет рабочего пространства, а зависимость пакета сохраняется, пока её использует вложенный под ним пакет. Когда tsx сохраняется, предупреждение называет то, что всё ещё его использует.

Конфигурации инструментов и исходные файлы нужно изменять вручную. Например, замените `nodeArguments: ['--import=tsx']` на `nodeArguments: ['--import=vite-plus/register']` или настройку Mocha `"import": "tsx"` на `"import": "vite-plus/register"`. Сохраните tsx, если проект использует его программные API.

О других различиях см. в разделе [Переход с tsx](/guide/vpx#coming-from-tsx).

### Переход с oxnode на `vpx` {#oxnode-to-vpx}

Миграция предлагает заменить `oxnode` — команду из `@oxc-node/cli` — на `vpx`. Она переписывает сценарии `package.json`, задачи lint-staged в `package.json` и JSON-файлах, а также shebang `#!/usr/bin/env oxnode`. Shebang с предзагрузкой Node.js, например `#!/usr/bin/env -S node --import @oxc-node/core/register`, сохраняют Node.js и используют `vite-plus/register`, в том числе в сценариях без расширения. Миграция сохраняет синтаксис `env`, флаги и относительные пути в shebang. В проекте, который уже использует Vite+, выполните `vp migrate --full`, чтобы включить эту миграцию.

| До                                                        | После                                                |
| --------------------------------------------------------- | ---------------------------------------------------- |
| `oxnode ./scripts/seed.ts`                                | `vpx ./scripts/seed.ts`                              |
| `oxnode -C dev ./build.ts`                                | `vpx -C dev ./build.ts`                              |
| `oxnode watch --include "config/*.json" ./server.ts`      | `vpx --watch --include "config/*.json" ./server.ts`  |
| `node --import @oxc-node/core/register ./scripts/seed.ts` | `node --import vite-plus/register ./scripts/seed.ts` |
| `NODE_OPTIONS='--import @oxc-node/core/register' mocha`   | `NODE_OPTIONS='--import vite-plus/register' mocha`   |

Формы `node --import @oxc-node/core/register` и `register.mjs` сохраняют Node.js, его обёртки, аргументы и встроенные режимы наблюдения, eval и тестирования. Буквальные присваивания `NODE_OPTIONS` тоже используют общедоступную предзагрузку. Команды, использующие исполняемый файл `oxnode`, вместо этого следуют правилам `vpx`: `oxnode --watch` остаётся без изменений, потому что запускает наблюдатель Node.js, а `oxnode watch` и `vpx --watch` используют наблюдатель oxc-node.

Команды, которые явно задают `OXC_TRANSFORM_ALL` в значение, отличное от `typescript`, остаются без изменений. Непустые присваивания `VP_SCRIPT_TSCONFIG` и `TSX_TSCONFIG_PATH` тоже остаются без изменений, потому что они изменили бы выбор конфигурации. Команды, которые читают файл окружения, остаются без изменений, потому что он может выбрать другой режим преобразования. Миграция проверяет названный сценарий и локальные предзагрузки на использование отдельного API oxc-node, который после миграции настроил бы другой загрузчик; импорты она не разбирает.

Пользовательские асинхронные хуки `--loader` и `--experimental-loader` сохраняют исходный порядок, когда меняется импорт register. Это позволяет использовать проектные загрузчики для разрешения и ресурсов вместе с загрузчиком TypeScript от Vite+. Это не означает совместимости со вторым преобразователем TypeScript или с произвольными синхронными цепочками `module.registerHooks()`.

Прямые команды `oxnode` и команды с предзагрузкой Node.js остаются без изменений, если дополнительный `--require` или `--import` может изменить настройки загрузчика. Команды Node.js тоже остаются без изменений, если встроенный код по-прежнему вызывает отдельные API oxc-node. Миграция проверяет явные локальные загрузчики в shebang относительно владеющего пакета на ссылки на отдельный API, не разбирая их импорты. Пути она оставляет без изменений: во время выполнения относительные пути загрузчиков берутся от рабочего каталога вызывающего, а не от каталога сценария.

Dev-зависимости `@oxc-node/cli` и `@oxc-node/core` удаляются только тогда, когда они больше нигде не нужны. Ссылки на загрузчики, импорты API, команды CI, хуки и shell-скрипты могут оставить эти зависимости установленными. Миграция также проверяет файлы, названные в `--env-file` и `--env-file-if-exists`, независимо от их имени. Если она не может найти или прочитать файл окружения, зависимости остаются для ручной проверки. Runtime- и peer-зависимости остаются на месте.

### Переход с ts-node на `vpx` {#ts-node-to-vpx}

Миграция предлагает заменить поддерживаемые команды ts-node на `vpx` только тогда, когда проверка типов явно отключена. Обычный `ts-node` проверяет типы перед выполнением; `vpx` этого не делает. Команды, которые всё ещё проверяют типы, остаются без изменений с предупреждением, даже если другая опция включает режим transpile-only.

| До                                                                                | После                                                               |
| --------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| `ts-node --transpileOnly ./scripts/seed.ts`                                       | `vpx ./scripts/seed.ts`                                             |
| `ts-node -T -P tsconfig.scripts.json ./scripts/seed.ts`                           | `vpx --tsconfig=tsconfig.scripts.json ./scripts/seed.ts`            |
| `ts-node-transpile-only ./scripts/seed.ts`                                        | `vpx ./scripts/seed.ts`                                             |
| `node -r ts-node/register/transpile-only ./scripts/seed.ts`                       | `node --import vite-plus/register ./scripts/seed.ts`                |
| `node --loader ts-node/esm/transpile-only ./scripts/seed.ts`                      | `node --import vite-plus/register ./scripts/seed.ts`                |
| `NODE_OPTIONS='--require ts-node/register/transpile-only' node ./scripts/seed.ts` | `NODE_OPTIONS='--import vite-plus/register' node ./scripts/seed.ts` |

Миграция также читает `transpileOnly` и `typeCheck` из локальных JSONC-файлов tsconfig, локальных цепочек `extends` и буквальных присваиваний `TS_NODE_TRANSPILE_ONLY` / `TS_NODE_TYPE_CHECK`. `-P`, `--project` и `TS_NODE_PROJECT` задают конфигурацию. Каталог, переданный в `-P` или `--project`, разрешается в его `tsconfig.json`; каталог в `TS_NODE_PROJECT` остаётся без изменений. Когда ts-node находит конфигурацию неявно, миграция закрепляет этот файл через `--tsconfig`, чтобы `vpx` использовал его на протяжении всего запуска. `ts-node-esm` и `--esm` поддерживаются, когда проверка типов отключена.

Если существующая конфигурация и её локальная цепочка `extends` не содержат ни `target`, ни `useDefineForClassFields`, команда остаётся без изменений с предупреждением. В этом случае ts-node по умолчанию использует семантику присваивания для полей класса, а `vpx` — семантику define. Задайте `compilerOptions.useDefineForClassFields` в `false`, чтобы сохранить семантику присваивания до миграции.

Поддерживаемые команды с предзагрузкой Node.js сохраняют Node.js и заменяют и старый параметр загрузчика, и сам модуль на `--import vite-plus/register`. Буквальные присваивания `NODE_OPTIONS` тоже мигрируют, когда они приводят к известной команде `node` и проходят те же проверки. Существующий выбор файла через `TS_NODE_PROJECT` остаётся на месте. Предзагрузка, которой нужно закрепить неявную конфигурацию, остаётся без изменений: задайте `TS_NODE_PROJECT` перед миграцией, потому что Node.js не принимает `--tsconfig`.

Предзагрузки тоже остаются без изменений, когда в рабочем каталоге нет конфигурации, но файл точки входа обнаружил бы другую. Миграция не сканирует импортированные модули на дополнительные файлы конфигурации.

Пользовательские компиляторы, транспайлеры, SWC, переопределения компилятора ts-node, неподдерживаемое наследование конфигурации, eval и использование REPL остаются без изменений. Файлы окружения, файлы конфигурации Node.js, дополнительные предзагрузки и неподдерживаемые присваивания `NODE_OPTIONS` тоже сохраняют исходную команду, потому что они могут изменить настройки ts-node до регистрации. Непустые присваивания `VP_SCRIPT_TSCONFIG`, `TSX_TSCONFIG_PATH` или `OXC_TSCONFIG_PATH` остаются без изменений, потому что они выбрали бы другую конфигурацию. Миграция проверяет названные сценарии на известные несовместимости модулей; импорты она не разбирает. Мигрированные сценарии используют [правила tsconfig и модулей `vpx`](/guide/vpx#tsconfig).

Точки входа со статическими импортами или реэкспортами значений CommonJS тоже остаются без изменений. Это включает именованные привязки, привязки пространства имён и привязки по умолчанию, файлы `.js` в пакетах CommonJS и точки входа пакетов. Миграция проверяет разрешение и через импорт, и через require, не выполняя зависимости. Неразрешённые цели и цели, различающиеся между этими режимами, остаются без изменений для ручной проверки. Даже `esModuleInterop: true` может развернуть значение CommonJS `__esModule.default` иначе, чем Node.js, поэтому сама по себе эта настройка не делает дефолтный импорт безопасным. Импорты и экспорты только типов, импорты, используемые ради побочных эффектов, проверенные цели ES-модулей и именованные встроенные привязки Node.js эту проверку не запускают.

Как и с oxnode, миграция переписывает сценарии пакета, задачи lint-staged в JSON и поддерживаемые env-shebang. Shebang, которым нужна закреплённая конфигурация, остаются без изменений, потому что путь к конфигурации зависит от рабочего каталога вызывающего. Существующие проекты Vite+ используют `vp migrate --full`. Dev-зависимость `ts-node` удаляется только тогда, когда она больше нигде не нужна: ни одной оставшейся команде, загрузчику, импорту API или ссылке на конфигурацию. Runtime- и peer-зависимости остаются, и `typescript` не удаляется.

## Правила непрерывной интеграции {#continuous-integration-rules}

Миграция заменяет точные ссылки на `voidzero-dev/setup-vp@v1` в рабочих процессах GitHub Actions и составных действиях в `.github` на последнюю точную версию `setup-vp`, известную этой версии Vite+. Замороженный тег `v1` больше не получает новых версий. Существующие точные версии и SHA коммитов остаются без изменений.

## Правила обработки версии Node.js {#node-js-version-rules}

Миграция преобразует закрепление Volta `volta.node` в `.node-version`, потому что Vite+ не читает Volta. В существующем проекте Vite+ это преобразование входит в состав полной настройки, поэтому выполняется при запуске `vp migrate --full`; для новых проектов оно выполняется всегда.

- Если существует `.node-version` или `.nvmrc`, миграция сохраняет его и пропускает преобразование Volta. Vite+ читает оба файла напрямую (см. [Выбор версии Node.js](/guide/env#node-js-selection)).

## Правила для менеджеров пакетов {#package-manager-rules}

### pnpm

**Расположение корневых настроек.** Начиная с pnpm 10.6.2, файл `pnpm-workspace.yaml` является единственным источником поддерживаемых корневых настроек. Во время миграции распознаваемые поля из `package.json#pnpm` переносятся туда, включая `overrides`, правила для peer-зависимостей, настройки патчей, расширения пакетов, параметры архитектуры и политики сборки, конфигурацию аудита и обновлений, а также зависимости конфигурации. Если объект `pnpm` становится пустым, он удаляется. Неизвестные ключи сохраняются, поскольку они могут использоваться другими инструментами.

- Если одинаковая переносимая настройка определена в обоих файлах, объекты объединяются рекурсивно, а уникальные элементы массивов сохраняются. При конфликте скалярных значений приоритет отдаётся значениям из `package.json#pnpm`, а остальные записи, существующие только в `pnpm-workspace.yaml`, сохраняются.
- До версии pnpm 10.6.2 эти настройки остаются в `package.json#pnpm`. (Поддержка настроек рабочего пространства появлялась постепенно: начиная с 10.5.0 — в общем случае, с 10.5.1 — для `overrides`, с 10.6.2 — для `peerDependencyRules`. Начиная с pnpm 11 устаревшие настройки в `package.json` больше не читаются.)

**Каталоги.** Каталоги — это отдельная возможность, поддерживаемая начиная с pnpm 9.5.0 и не зависящая от описанного выше расположения настроек. Даже в версиях ниже 10.6.2, где `overrides` остаются в `package.json#pnpm`, миграция всё равно обновляет каталог рабочего пространства, заменяя устаревшие алиасы-обёртки, и сохраняет `catalog:` в `overrides` как ссылки, а не подставляет вместо них конкретные версии.

- Ссылки на зависимости, стандартный и именованные каталоги, `overrides` и `peerDependencyRules` поддерживаются в согласованном состоянии.
- pnpm допускает определение стандартного каталога либо через корневое поле `catalog`, либо через `catalogs.default`, но не одновременно. Миграция сохраняет уже используемый вариант и никогда не создаёт второй параллельно.
- Если существующий именованный каталог уже содержит записи для `vite-plus`, `vite` или `vitest`, миграция использует этот каталог набора инструментов и для новых зависимостей и `overrides`. Новый стандартный каталог верхнего уровня создаётся только в том случае, если невозможно использовать существующий стандартный или именованный каталог.

**Правила для peer-зависимостей.** Версия ядра кодирует версию Vite, входящую в состав пакета: ядро `8.3.5000` содержит Vite `8.3.5` (см. [RFC](https://github.com/voidzero-dev/vite-plus/blob/main/rfcs/core-version-alignment.md)). pnpm проверяет диапазоны peer-зависимости `vite` по алиасу `vite`, поэтому плагин, поддерживающий входящий в состав Vite, проходит проверку, а плагин, который его не поддерживает, — нет.

- Миграция не добавляет `vite` в `peerDependencyRules.allowAny` или `peerDependencyRules.allowedVersions`.
- Миграция удаляет `vite` из `allowAny` и удаляет `allowedVersions.vite`, если его значение равно `'*'`, — в том числе если запись добавили вы сами. Такие записи принимали алиас ядра `1.x`. Другой диапазон `allowedVersions.vite`, например `'7 || 8'`, сохраняется. Миграция удаляет поле, а если не осталось ни одной записи — и сам `peerDependencyRules`. Другие записи сохраняются. В сводке миграции называется удалённое правило.
- Для preview-сборки (`0.0.0-commit.<sha>`) или предрелизной версии ядра Vite+ (например, `8.4.0-vp.0`) миграция продолжает записывать правило `vite`. Менеджеры пакетов не принимают такие версии для диапазонов вида `^8.0.0`.
- В pnpm до версии 10.2.0 миграция тоже продолжает записывать правило `vite`. Эти версии применяют переопределение-алиас `vite@*` к диапазонам peer-зависимостей, поэтому без правила любая peer-зависимость `vite` не проходит проверку на соответствие ядру.
- После миграции плагин, чей диапазон peer-зависимости `vite` исключает входящий в состав Vite (например, `^7.0.0`), вызывает предупреждение о peer-зависимости. С `strictPeerDependencies` установка завершается с ошибкой. Обновите плагин или расширьте диапазон peer-зависимости только этого плагина:
  - pnpm 12.17.0 и новее: добавьте переопределение `'vite-plugin-foo>vite:peer': '*'`. В этой версии pnpm объявил `peerDependencyRules` устаревшим.
  - Более ранние версии pnpm: добавьте правило `allowedVersions: { 'vite-plugin-foo>vite': '*' }`.

  Миграция удаляет только обычный ключ `vite`, поэтому обе формы сохраняются.

**Другие правила.**

- Пакеты, которые используют `vite-plus` без прямого объявления `vite`, сохраняют такую структуру (см. [Vite и overrides](#vite-and-overrides)).
- Не связанные с миграцией `overrides` в виде селекторов или объектов сохраняются.

### npm

- Прямые алиасы нормализуются до добавления соответствующего `override`, чтобы npm не завершался с ошибкой `EOVERRIDE`.
- Если обычная установка Vite заменяется алиасом ядра, перед повторной установкой удаляются устаревшие данные установки Vite и lock-файла.
- При использовании дополнительных браузерных провайдеров добавляется зависимость верхнего уровня `vite`, если без неё вложенные пакеты Vitest не могут её разрешить.

### Yarn

- Vite+ не поддерживает Plug'n'Play. Миграция обнаруживает явное и неявное использование PnP и переводит проект на `nodeLinker: node-modules`, сохраняя все остальные настройки `.yarnrc.yml`. При использовании `--no-interactive` преобразование выполняется автоматически. Если установлен `YARN_NODE_LINKER=pnp` на уровне процесса, пользователь должен изменить его самостоятельно.
- Ссылки на каталоги и пользовательские настройки hoisting сохраняются.
- Миграция предотвращает появление нескольких экземпляров Vitest при изолированном hoisting в рабочих пространствах: если возможно, применяется исправление на уровне пакета, а если безопасно изменить конфигурацию нельзя — выводится предупреждение.

### Bun

- Каталоги Bun разрешаются только внутри рабочего пространства — корневого `package.json` с полем `workspaces`. Пустое поле `workspaces` тоже подходит. В рабочем пространстве Bun сохраняются существующие расположения каталогов верхнего уровня или рабочего пространства, а также ссылки на именованные каталоги. Отдельный проект Bun без `workspaces` сохраняет конкретные спецификации и не получает поля каталога, потому что `bun install` не умеет разрешать `catalog:` вне рабочего пространства.
- Bun до версии 1.2.21 читает только каталоги из `workspaces`. На этих версиях миграция использует каталоги только тогда, когда проект уже имеет каталог в `workspaces`, а в остальных случаях сохраняет конкретные спецификации.
- Если существующий именованный каталог уже содержит записи для `vite-plus`, `vite` или `vitest`, миграция добавляет недостающие записи набора инструментов в этот каталог, а не создаёт рядом с ним стандартный каталог.
- Алиас ядра дублируется как прямая зависимость `vite`, чтобы Bun мог обнаружить поставщика peer-зависимости до применения `overrides`.

## После миграции {#after-the-migration}

- Каждый файл конфигурации Vite проверяется на наличие конструкций, несовместимых с Rolldown (например, `manualChunks`). Все найденные проблемы выводятся в виде предупреждений, но конфигурация автоматически не изменяется.
- Зависимости переустанавливаются один раз для обновления lock-файла. Если установка завершается ошибкой, миграция сообщает об этом и завершается с ненулевым кодом.
- После успешной миграции выполняется `vp fmt` для файлов, изменённых в процессе миграции, за исключением путей, которые уже содержали несохранённые изменения в рабочем дереве Git. Oxfmt самостоятельно определяет поддерживаемые форматы файлов; в проектах без Git форматируется весь проект. Форматирование пропускается, если проект всё ещё использует Prettier. Ошибка форматирования выводится как предупреждение, чтобы результаты миграции сохранились, а пользователь мог вручную выполнить команду форматирования.
