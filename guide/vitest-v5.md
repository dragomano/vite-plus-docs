# Обновление до Vitest 5 {#upgrade-to-vitest-5}

Vite+ включает Vitest `5.0.1`. Для CLI и тестов используйте Node `^22.18.0 || ^24.11.0 || >=26.0.0`.

## Перед миграцией {#before-you-migrate}

Выполните `vp migrate` из корня workspace до ручного обновления зависимостей. Сохраните исходный lock-файл и установленные пакеты, чтобы миграция могла определить исходную версию Vitest, включая раннер внутри более старой установки `vite-plus`.

Проекты с версией Vitest ниже 4 сначала обновите до v4, а затем запускайте эту миграцию. Если исходную версию определить не удаётся, восстановите и установите исходный lock-файл, затем повторно выполните `vp migrate`.

```bash
vp migrate
vp install
vp check
vp test
```

Прочитайте отчёт с указанием конкретных файлов перед фиксацией результата. Миграция останавливается до обновления зависимостей при наличии конфликтующих настроек `test.api` и `test.browser.api` или удалённых runtime API, для которых нет поддерживаемой замены. Устраните эти блокирующие проблемы и снова выполните команду. Безопасные изменения можно завершить с успешным статусом выхода, даже если в отчёте остаются пункты для проверки.

Вы можете сохранить эквивалентные статические значения `test.api` и `test.browser.api`, включая объекты с разным порядком свойств или стилем кавычек. Миграция удаляет избыточный `browser.api`. Для конфликтующих значений или выражений, требующих вычисления, выберите одну конфигурацию; в v5 используется один API-сервер.

## Среда выполнения Node.js {#node-runtime}

Перед установкой зависимостей миграция обновляет несовместимые фиксации версии среды выполнения до ближайшего поддерживаемого минимума. Например, `20.19.0` преобразуется в `22.18.0`, `24.10.0` — в `24.11.0`, а `25.9.0` — в `26.0.0`. Поддерживаемые фиксации остаются без изменений. Неразрешённые селекторы всё ещё требуют проверки.

Отдельно учитывайте публичное ограничение `engines.node` вашей библиотеки и среду выполнения для тестов. Миграция не изменяет это ограничение. Проверять диапазон engine с поддерживаемым минимумом, например `>=22.19.0`, или целиком поддерживаемую основную версию, например `24.x`, не требуется. Используйте конкретную фиксацию среды выполнения, соответствующую поддерживаемому минимуму или превышающую его для этой основной версии.

Проверки совместимости Node.js охватывают `.node-version`, `.nvmrc`, а также объявления `engines.node`, `devEngines.runtime` и `volta.node` в `package.json`. Версии Node.js в CI workflow, контейнерах и других файлах не входят в область этих проверок.

## Сохранение существующего поведения {#preserve-existing-behavior}

Для preview-сборок ссылки ведут на сайт документации Vite+ для соответствующего PR. В релизных сборках используется `viteplus.dev`. Ссылки на документацию исходного Vitest остаются без изменений.

Для конфигураций v4 миграция добавляет настройки совместимости, если соответствующий параметр не был указан. Явно заданные настройки имеют приоритет. Рядом с каждой добавленной настройкой вы получите комментарий с причиной её добавления, рекомендациями по переходу на поведение v5 и ссылками на контрольный список очистки и руководство по миграции Vitest:

```ts
test: {
  // Совместимость с Vitest v4: сохраняет историю вызовов моков.
  // Удалите после того, как тесты перестанут зависеть от вызовов из setup или предыдущих тестов.
  // https://viteplus.dev/guide/vitest-v5#remove-unneeded-compatibility-settings
  // https://vitest.dev/guide/migration/#clearmocks-is-enabled-by-default
  clearMocks: false,
}
```

| Добавленная настройка                                                                                                  | Поведение, которое нужно проверить перед её удалением                                                                                       |
| ---------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| [`test.clearMocks: false`](https://vitest.dev/guide/migration/#clearmocks-is-enabled-by-default)                     | Проверьте утверждения, зависящие от вызовов моков из `setup`, `beforeAll` или предыдущих тестов. V5 очищает эту историю перед каждым тестом. |
| [`test.sharedViteServer: false`](https://vitest.dev/guide/migration/#inline-projects-share-the-vite-server-by-default) | Проверьте плагины и хуки конфигурации, использующие общий сервер. V5 инициализирует их один раз для подходящих inline-проектов.              |
| [Inline `extends: false`](https://vitest.dev/guide/migration/#inline-projects-inherit-the-root-config-by-default)  | Проверьте унаследованные параметры корневой конфигурации, плагины и файлы setup. V5 объединяет массивы, поэтому избегайте дублирования setup. |
| [`browser.locators.exact: false`](https://vitest.dev/guide/migration/#locators-are-strict-by-default)                | Обновите локаторы для полного совпадения с учётом регистра или отключите строгость для отдельных локаторов.                                  |
| [Glob-порог `perFile: true`](https://vitest.dev/guide/migration/#glob-coverage-thresholds-no-longer-inherit-perfile) | Оставьте его для проверки покрытия каждого файла. Удалите, чтобы проверять соответствующие файлы как группу.                                |
| [`fakeTimers.toNotFake: ['Temporal']`](https://vitest.dev/guide/migration/#fake-timers-and-setsystemtime-now-mock-temporal) | Проверьте тесты, использующие глобальный полифилл Temporal с поддельными таймерами. Удалите только `Temporal`, чтобы использовать замоканное время; остальные исключения сохраните. |

Новые проекты используют значения по умолчанию v5. Возможно, некоторые сгенерированные настройки совместимости удастся удалить без изменений в коде или с небольшими локализованными исправлениями. Перед их удалением выполните приведённые ниже проверки. Эти параметры по-прежнему поддерживаются в v5; пока оставьте настройки совместимости, если их удаление требует значительных изменений тестов.

Миграция оставляет существующие настройки и комментарии без изменений. Она не добавляет комментарии к настройкам из предыдущей миграции, поскольку не может отличить такие настройки от сделанных вами самостоятельно. Повторные запуски не дублируют комментарии и не восстанавливают удалённые вами комментарии.

Если в проекте нет конфигурации тестов, можно использовать значения v5 по умолчанию без запроса на проверку и создания новой конфигурации совместимости. Другие этапы миграции, например объединение конфигурации линтера, могут создать `vite.config.ts`; настройки совместимости с v4 применяются к этой новой конфигурации в рамках той же миграции.

После обновления до v5 можно повторно выполнить `vp migrate`, не применяя заново значения совместимости с v4, в том числе в проектах без конфигурации. Перед повторным запуском миграции завершите установку зависимостей.

Устраните замечания из отчёта первой миграции или сохраните его перед удалением исходных зависимостей. Последующие запуски используют текущую версию Vitest и текущие файлы, поэтому они могут не повторить проверки, которые зависели от исходного поведения v4.

### Удаление ненужных настроек совместимости {#remove-unneeded-compatibility-settings}

Сначала проверьте мигрированный проект с сохранёнными настройками совместимости. Затем используйте diff миграции и комментарии `Vitest v4 compatibility`, чтобы определить добавленные настройки в корневой, workspace- и inline-конфигурациях проектов. Существующие пользовательские настройки и настройки с неясным происхождением оставьте без изменений.

Удаляйте по одной добавленной настройке за раз. Проверьте, какое значение использует проект после удаления, включая унаследованные параметры, плагины и файлы setup. Сначала запустите затронутые наборы тестов без изменений в коде. При необходимости включите проверки браузера и покрытия; успешно прошедший набор тестов Node.js не подтверждает корректность браузерных локаторов. Для `fakeTimers.toNotFake` удаляйте только добавленную запись `Temporal`, сохраняя остальные исключения.

Можно вносить небольшие локализованные исправления в приложение, тесты или setup, сохраняющие смысл тестов, например исправить локатор или скорректировать настройку моков в нескольких тестах. Сохраняйте утверждения и покрытие тестами без изменений и проверяйте все изменения снимков. Если удаление требует массового редактирования тестов или рефакторинга общего setup, пока оставьте совместимость и зафиксируйте последующую работу.

Сохраняйте удаление, если затронутые тесты проходят, тот же набор тестов запускается без новых пропусков и подтверждает получившееся поведение. Также удалите сгенерированный комментарий. Восстановите настройку и комментарий, если проверка по-прежнему завершается ошибкой, необходимые наборы тестов невозможно запустить или результат остаётся неопределённым. Отменяйте только пробные изменения, связанные с очисткой; завершённые исправления миграции и несвязанные изменения сохраняйте. Различайте отложенный рефакторинг и настройку, которую не удалось проверить.

Успешно прошедшие тесты не доказывают, что проверка покрытия осталась неизменной. Сохраняйте сгенерированные настройки glob-порогов `perFile: true`, если только вы намеренно не хотите перейти от порогов для каждого файла к совокупной проверке. Для такого изменения агент должен запросить ваше подтверждение. См. [миграцию порогов покрытия в Vitest](https://vitest.dev/guide/migration/#glob-coverage-thresholds-no-longer-inherit-perfile).

После отдельных проверок запустите полный набор проверок со всеми принятыми удалениями. Для каждого кандидата укажите путь к конфигурации, решение об удалении, изменения в коде, команды проверки и их результаты, а также оставшуюся работу. Если вы оставляете параметр как решение проекта, замените его комментарий о совместимости на объяснение причины.

## Изменения исходного кода {#source-changes}

Для целевых изменений миграция использует синтаксис и привязки импортов. Для динамических параметров, неоднозначных обёрток или callback, контракт которого не допускает `async`, создаётся пункт для проверки.

```ts
// До
test.sequential('result', () => {
  expect(result).resolves.toBe(42);
});

// После
test('result', { concurrent: false }, async () => {
  await expect(result).resolves.toBe(42);
});
```

В браузерных тестах используйте `toMatchTextContent` для строковых утверждений и утверждений с регулярными выражениями в v4. Строковый матчёр v4 принимал частичный текст, поэтому идентичный текст в фикстуре не доказывает, что вы намеревались использовать точное совпадение из v5. Если вам нужна новая семантика, самостоятельно выберите `toHaveTextContent`.

Утверждения `@testing-library/jest-dom` в Node оставляйте без изменений. В пакете, содержащем одновременно Node- и браузерные тесты, миграция проверяет статическую принадлежность проекта перед переименованием матчёра. Необходимо проверить общие файлы, динамические конфигурации и переопределения браузера через командную строку. Вызовы через `expect.element()` однозначно указывают на браузерные утверждения.

Ожидайте `render` из `vitest-browser-vue` и `vitest-browser-svelte` перед тем, как обращаться к его результату. Замените `toThrow('')` и `toThrowError('')` на `/^$/`, чтобы сохранить утверждения для пустого сообщения.

При программной загрузке конфигурации замените деструктуризацию `{ viteConfig, vitestConfig }` возвращаемым значением `resolveConfig()` и его свойством `.test`. Для напрямую мигрированных команд `vitest list` добавляется `--no-static-parse`; поддерживаемые вызовы `Vitest.collect(filters, options)` получают `{ staticParse: false }`. Если вы хотите использовать статический сбор v5, сохраните явное указание `staticParse`.

## Бенчмарки {#benchmarks}

Используйте прямые вызовы `bench` со встроенными callback без аргументов или со ссылками на неизменённые локальные функции. Можно использовать динамические имена: миграция захватывает их один раз при регистрации. Она сохраняет callback рабочей нагрузки и запускает его через фикстуру v5 `bench` внутри теста. Простые вызовы `bench.skip`, `bench.only` и `bench.todo` превращаются в соответствующие модификаторы тестов. Вызовы внутри обычных callback `describe` и `suite` сохраняют окружающие их области видимости.

```ts
// До
import { bench } from 'vitest';
bench('parse', () => JSON.parse('{"value":1}'));

// После
import { test } from 'vitest';
test('parse', async ({ bench }) => {
  await bench('parse', () => JSON.parse('{"value":1}')).run();
});
```

Сохраняйте файлы бенчмарков, соответствующие `benchmark.include`. Команды `vitest bench` и `vp test bench` по-прежнему поддерживаются. Миграция их не удаляет.

Вы можете перенести встроенные настройки `benchmark.reporters` (`default` и `verbose`), а также литеральные пути `benchmark.outputFile` или `benchmark.outputJson` в reporters верхнего уровня. Существующие назначения reporters имеют приоритет перед предлагаемым переносом: вручную разрешите конфликтующие пути, выбор терминального reporter и потребителей JSON из stdout. Настройки, специфичные для проекта, слияния конфигураций, а также пользовательские или динамические reporters также требуют проверки. В v5 обычные тесты и бенчмарки используют общие reporters.

Для такой литеральной команды, как `vitest bench --outputJson=bench.json`, миграция выбирает JSON reporter и сохраняет путь к файлу. JSON-отчёт v5 содержит результаты тестов с бенчмарками для каждого теста. Если вы используете эти отчёты за пределами Vitest, обновите обработчики, ожидающие формат v4.

Проверьте вызовы с параметрами бенчмарков, импортированными или переназначенными callback, параметрами callback или обёртками. Базовые настройки `compare` и флаги `--compare` остаются блокирующими проблемами. Настройте хранение результатов для каждого бенчмарка и явное сравнение внутри теста. См. [руководство по миграции бенчмарков Vitest](https://vitest.dev/guide/migration/#benchmarking-api-rewrite) и [руководство по бенчмаркам](https://vitest.dev/guide/benchmarking) для вариантов замены. Используйте `bench.compare()`, если вам нужна таблица сравнения для нескольких рабочих нагрузок.

## Точки входа и пакеты {#entry-points-and-packages}

Используйте `vite-plus/test` для утверждений и поддерживаемых API раннера. Версии провайдеров покрытия и `@vitest/ui` должны в точности соответствовать версии встроенного раннера — `5.0.1`. Если проект использует `@vitest/web-worker`, сохраняйте для него ту же версию.

| Импорт v4                              | Импорт или действие в v5                                                        |
| -------------------------------------- | -------------------------------------------------------------------------------- |
| `vitest/coverage`, `vitest/reporters`  | `vite-plus/test/node`                                                           |
| `vitest/environments`, `vitest/snapshot` | `vite-plus/test/runtime`                                                        |
| `vitest/mocker`                         | `vite-plus/test/mocker`                                                         |
| `vitest/runners`, `vitest/suite`       | Проверьте `TestRunner` и его статические методы из `vite-plus/test`.            |
| Совместимые с корнем символы `@vitest/expect` | `vite-plus/test`; проверьте неподдерживаемые вспомогательные функции.       |
| `@vitest/runner`                        | Перенесите поддерживаемые символы в корневой API и проверьте остальные импорты. |
| `vitest/internal/module-runner`        | Переработайте интеграцию; публичной замены не существует.                      |
| `@vitest/ws-client`                     | Оставьте при необходимости; upstream больше не добавляет функции v5.           |

Vite+ 1.0 удаляет `vite-plus/test/coverage`, `/reporters`, `/environments` и `/snapshot`. Запустите `vp migrate`, чтобы переписать существующие импорты Vite+ на те же точки входа `node` или `runtime`, показанные выше. Vite+ сохраняет `vite-plus/test/mocker` для отдельного API `@vitest/mocker`. Частичные шимы для runner или expect plugin не предоставляются.

## Провайдер WebDriverIO от сообщества {#community-webdriverio-provider}

Vite+ 1.0 удаляет экспорты `vite-plus/test/browser-webdriverio`. Используйте `@vitest/browser-webdriverio` и выбирайте версию провайдера и peer-зависимости фреймворка, совместимые с вашими тестами. Это пакет, который сообщество поддерживает по собственному графику выпусков.

`vp migrate` заменяет устаревшие импорты провайдера на `@vitest/browser-webdriverio` и обеспечивает использование версии провайдера не ниже `5.0.0`. Если провайдер отсутствует, добавляется `^5.0.0`; более старые версии обновляются, а диапазоны, которые всё ещё допускают v4, сужаются. Также обновляются соответствующие записи каталогов и удаляются переопределения, принудительно задающие более старую версию провайдера. Версии и диапазоны, уже превышающие этот минимум, остаются без изменений. Миграция обеспечивает установку требуемой peer-зависимости `webdriverio`, не обновляя существующую версию фреймворка.

Для проектов, использующих этот провайдер, `vp migrate` добавляет переопределение `@vitest/browser`, соответствующее входящей в комплект версии Vitest. В Yarn используется `resolutions`. Это не позволяет диапазону версий провайдера сохранить более старый пакет браузера в lock-файле.

После этой миграции обновлением провайдера управляете вы; Vite+ не синхронизирует выпуски сообщества с Vitest. Существующие импорты из пакета сообщества остаются без изменений. Для пользовательских зависимостей, которые мигратор не может проверить, устраните диагностическую ошибку перед повторной попыткой миграции. См. [руководство по миграции исходного пакета](https://vitest.dev/guide/migration/#package-migration).

Устаревшие импорты Vite+ WebDriverIO `/context` переносятся в `vite-plus/test/browser/context`. Используйте эту общую точку входа для runtime API браузера; точка входа `/context` провайдера сообщества содержит только типы.

Необязательное объявление peer-зависимости по-прежнему определяется метаданными зависимостей Vitest. Оно не предоставляет экспорт Vite+ и не синхронизирует выпуски провайдера.

## Отчёты и снимки экрана {#reports-and-screenshots}

Миграция не изменяет и не сообщает об изменениях, затрагивающих только форматирование заголовков, вывод отчётов, пути к артефактам или устаревание зависимостей. Она оставляет обычные настройки reporters без изменений и не добавляет `stdout: true`. Удалённые API и флаги бенчмарков по-прежнему требуют миграции, чтобы команды могли выполняться.

Если вы используете сгенерированные отчёты или артефакты за пределами Vitest, проверьте эти пути. Сохраняйте старые записи в ignore-файлах, пока файлы остаются в этих каталогах. Миграция добавляет `.vitest/` в `.gitignore`, не удаляя старые записи.

| Вывод               | Значение по умолчанию в v4     | Значение по умолчанию в v5                    |
| ------------------- | ------------------------------ | --------------------------------------------- |
| Вложения            | `.vitest-attachements/`        | `.vitest/attachments/`                        |
| Снимки экрана ошибок | `__screenshots__/`             | `.vitest/attachments/failure-screenshots/`    |
| Blob-отчёты         | `.vitest-reports/blob-*.json`  | `.vitest/blob/blob-*.json`                    |
| HTML                | `html/index.html`              | `.vitest/index.html`                          |
| JSON                | stdout                         | `.vitest/json/output.json`                    |
| JUnit               | stdout                         | `.vitest/junit/output.xml`                    |

Теперь параметры HTML reporter используют `outputDir` вместо `outputFile`, принимающего путь к файлу. Если вам нужен пользовательский путь назначения, самостоятельно задайте `outputDir`. Остальные reporters по-прежнему поддерживают `outputFile`. См. [изменения в upstream, касающиеся отчётов](https://vitest.dev/guide/migration/#generated-reports-and-artifacts-use-the-vitest-directory).

Скопируйте пользовательский `browser.screenshotDirectory` в `browser.expect.toMatchScreenshot.screenshotDirectory`. Проверьте эталонные изображения перед их перемещением или повторной генерацией: в v4 они могли сохраняться в непредназначенном для этого месте. Каталог эталонных снимков экрана по умолчанию по-прежнему остаётся `__screenshots__`.

## Устранение замечаний миграции {#resolve-migration-findings}

Каждый элемент `BLOCK` или `REVIEW` для Vitest v5 содержит ссылку `Docs`. Перейдите по ссылке, чтобы ознакомиться с соответствующим изменением API или правилом миграции. Блокирующая проблема останавливает обновление зависимостей; элемент для проверки требует проверить результат, но не препятствует безопасным изменениям.

Для динамических конфигураций или общих файлов определите фактические настройки проекта Vitest перед редактированием. Разрешите функции конфигурации, spread-операторы и внешнее наследование либо внесите изменения совместимости вручную. В проекте со смешанными раннерами определите, какой раннер отвечает за неимпортированные глобальные переменные.

При ошибках парсера или пересекающихся изменениях сохраните исходный файл и внесите документированное изменение вручную. После устранения проблемы снова запустите `vp migrate`. Успешное завершение всё ещё может содержать элементы для проверки; сохраняйте этот отчёт, пока не завершите ручные изменения.

## Чек-лист проверки {#review-checklist}

Используйте расположение файлов из отчёта миграции, чтобы проверить эти изменения. Запустите наборы тестов для браузера и покрытия, а также тесты Node.

Для типов матчёров jest-dom подключите `@testing-library/jest-dom/vitest` в `compilerOptions.types` или импортируйте его из TypeScript-файла setup, который включён в `tsconfig.json`. Корневая запись типов `@testing-library/jest-dom` расширяет Jest. JavaScript-файл setup, исключённый параметром `allowJs: false`, не загружает расширение типов Vitest при проверке типов. Перед изменением записей типов проверьте общие конфигурации Jest/Vitest.

С `vitest@5.0.1` предварительная загрузка объявлений браузера также может привести к тому, что TypeScript будет отклонять допустимые утверждения jest-dom для Node: `toHaveTextContent(/pattern/)` и пользовательские CSS-свойства в `toHaveStyle()`. Мы воспроизвели этот конфликт как с upstream-импортами, так и с импортами Vite+. Проблема воспроизводится как с `@testing-library/jest-dom@6.9.1`, так и с `7.0.1`. Проверьте объявления, загружаемые каждым `tsconfig.json` для тестов; одного добавления записи типов jest-dom может быть недостаточно для устранения конфликта. Оставьте затронутый проект на выпуске на основе v4, пока типы матчёров Node и браузера не будут проходить отдельные проверки.

| Область                | Что необходимо проверить                                                                                                                                                                    |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Выбор тестов           | Полные имена используют разделители `>`. Проверьте фильтры имён, охватывающие границы между suite; простые фильтры из одного сегмента проверять не нужно. |
| Поднятые моки          | Перенесите вложенные вызовы `vi.mock`, `vi.unmock` и `vi.hoisted` на верхний уровень после проверки захватываемых переменных.                                                              |
| Автомоки браузера      | Моки без фабрики сохраняют значения по умолчанию. Если нужны реальные реализации, выберите `{ spy: true }`.                                                                               |
| Моки конструкторов     | Проверьте прототипы, методы и `instanceof` для `vi.fn`, `vi.spyOn` и `mockImplementation`.                                                                                                  |
| Бенчмарки              | Проверьте вызовы бенчмарков, которые миграции не удалось преобразовать, группы сравнения и удалённые параметры отчётности. Сохраняйте поддерживаемые параметры, такие как `benchmark.enabled` и `benchmark.include`. |
| Асинхронные утверждения | Ожидайте или возвращайте `resolves`, `rejects`, снимки файлов, polling и браузерные утверждения. Проверьте тайм-ауты `expect.poll`, не увеличивая их, чтобы скрыть ошибки.               |
| Типы матчёров          | Обновите старые объявления `Assertion<T>`, `Matchers<T>` и `jest.Matchers`, добавив параметры типов возвращаемого значения и полученного значения.                                        |
| Команды браузера       | Принимайте объекты `SerializedLocator` вместо строк селекторов.                                                                                                                            |
| Интерфейс браузера     | Используйте URL, выводимые Vitest, включая UI-токены и `sessionId` оркестратора. Проверяйте скриншоты в режимах с отображением и без отображения браузера при фиксированных размерах viewport. |
| Конфигурация проекта   | Проверьте динамические проекты, слияния корневой конфигурации, вложенные проекты и хуки, предполагающие один сервер или одно выполнение конфигурации на проект.                           |
| Сбор тестов            | Проверьте динамические обёртки команд и программные вызовы `collect()`, параметры статического парсинга которых требуют ручного редактирования.                                          |
| Покрытие               | Сравните разрешённые наборы файлов v4/v5 для заданных `coverage.include` и `coverage.exclude`. Сопоставление относительных путей может изменить измеряемый набор.                         |
| ID воркеров            | Проверьте арифметику и индексацию, основанные на `VITEST_POOL_ID` или `VITEST_WORKER_ID`; ID начинаются с 1.                                                                              |
| Пользовательские окружения | Восстановите записи `populateGlobal().originals` с помощью `Object.defineProperty`; карта содержит дескрипторы.                                                                         |
| Глобальные DOM-объекты  | Проверьте присваивания в тестах jsdom/happy-dom; присваивания глобальным объектам также обновляют `window`.                                                                                |
| Temporal               | Проверьте области кода, использующие Temporal и `vi.setSystemTime()`. `toNotFake` не сохраняет прежнее поведение без fake timers.                                                          |
| Удалённые API          | Замените неподдерживаемые импорты runner и внутренних модулей до обновления пакетов. Ссылки, используемые только для типов, также требуют проверки и проверки типов.                       |

## Запуск ниже каталога конфигурации {#run-below-a-config-directory}

Vitest v5 больше не выполняет поиск конфигурации в родительских каталогах. Из подкаталога передайте и родительскую конфигурацию, и нужный каталог с тестами:

```bash
vp test --config ../vite.config.ts --dir .
```

См. [руководство по миграции на Vitest 5](https://vitest.dev/guide/migration/) в upstream для примеров API и нового подхода к бенчмаркам.
